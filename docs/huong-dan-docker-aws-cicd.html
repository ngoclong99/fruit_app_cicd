1. Docker là gì? Tại sao cần dùng?

Docker là công cụ giúp đóng gói ứng dụng cùng toàn bộ thứ nó cần (Node.js, thư viện, config…) vào một "hộp" gọi là container. Container chạy giống hệt nhau trên mọi máy — máy dev, máy bạn đồng nghiệp, hay server AWS.

🔑 Vấn đề Docker giải quyết Trước đây hay xảy ra tình trạng "chạy trên máy tôi được mà máy khác không chạy" vì khác phiên bản Node, khác OS, thiếu thư viện… Docker đóng gói tất cả lại, đảm bảo môi trường luôn nhất quán.

1.2 Thứ tự tạo ra các thành phần trong Docker

Các thành phần Docker không xuất hiện cùng lúc — chúng được tạo ra theo một thứ tự nhất định, mỗi thứ phụ thuộc vào thứ trước đó.

Bức tranh tổng thể

Dockerfile ──build──▶ Image ──run──▶ Container │ sử dụng ┌────┴─────┐ Volume Network (tạo trước) (tạo trước)

BƯỚC 1 — Bạn viết Dockerfile (thủ công)

Đây là file bạn tự viết, chưa có gì xảy ra trong Docker cả. Dockerfile chỉ là tập lệnh hướng dẫn — giống như công thức nấu ăn, chưa nấu.

FROM node:20-alpine      # dùng nguyên liệu gì
WORKDIR /app             # chuẩn bị bếp ở đâu
COPY package*.json ./    # chuẩn bị nguyên liệu
RUN npm install          # bước chế biến
COPY . .
CMD ["node", "index.js"] # món ăn xong, serve thế nào

BƯỚC 2 — docker build → tạo ra Image

Docker đọc Dockerfile từ trên xuống, mỗi lệnh tạo ra một layer (lớp). Các layer được xếp chồng lên nhau thành Image hoàn chỉnh.

Layer 5: CMD ["node", "index.js"] ← mỏng nhất Layer 4: COPY . . Layer 3: RUN npm install ← lớn nhất (node_modules) Layer 2: COPY package.json Layer 1: FROM node:20-alpine ← base layer ───────────────────────────────────────── Image hoàn chỉnh (~180MB) read-only, bất biến
🔑 Image là bất biến (read-only) Sau khi build xong không thể sửa. Muốn thay đổi phải build lại Image mới.

Layer caching — Tại sao COPY package.json trước?

# Lần build 1: build hết tất cả — mất 60 giây
FROM → COPY pkg.json → RUN npm install → COPY src → CMD

# Lần build 2: chỉ sửa code, không đổi package.json
FROM [cache] → COPY pkg.json [cache] → npm install [cache] → COPY src [BUILD LẠI] → CMD
# → chỉ mất 3 giây vì 3 layer đầu được cache lại!

BƯỚC 3 — docker run → tạo ra Container

Docker lấy Image (read-only) và thêm một writable layer lên trên. Mọi thay đổi trong quá trình chạy (log, file tạm…) đều ghi vào layer này.

┌──────────────────────────────────────────┐ │ Writable Layer (container layer) │ ← CHỈ tồn tại khi container sống ├──────────────────────────────────────────┤ │ Layer 5: CMD │ │ Layer 4: COPY . . │ ← Image layers (read-only) │ Layer 3: RUN npm install │ dùng chung nếu nhiều container │ Layer 2: COPY package.json │ cùng Image │ Layer 1: FROM node:20-alpine │ └──────────────────────────────────────────┘
⚠️ Container bị xóa → writable layer mất hết Image vẫn còn nguyên — có thể tạo container mới từ cùng Image đó. Để dữ liệu không mất, phải dùng Volume.

BƯỚC 4 — Volume — tạo trước hoặc cùng lúc với container

Mục đích: dữ liệu không bị mất khi container bị xóa. Có 2 loại:

Named VolumeBind Mount
Cú pháppostgres_data:/var/lib/..../backend/src:/app/src
Ai quản lýDocker tự quản lý vị trí lưuBạn chỉ đường dẫn cụ thể trên máy
Dùng choDatabase, uploads — dữ liệu quan trọngHot-reload khi dev — sửa code thấy ngay
Tồn tạiĐến khi docker compose down -vThư mục trên máy host luôn còn

Timeline của Volume:

docker compose up lần 1
    │
    ├─▶ Docker kiểm tra: volume "postgres_data" tồn tại chưa?
    │       Chưa có → TẠO MỚI volume (rỗng)
    │       Đã có   → DÙNG LẠI (dữ liệu cũ vẫn còn!)
    │
    └─▶ Gắn volume vào container tại /var/lib/postgresql/data

docker compose down      # container bị xóa, volume VẪN CÒN
docker compose down -v   # container + volume đều bị xóa (mất data!)

BƯỚC 5 — Network — tạo trước container

Network được tạo trước container để các container biết cách tìm nhau qua tên service.

docker compose up
    │
    ├─▶ 1. Tạo Network "app-net"            (nếu chưa có)
    ├─▶ 2. Tạo Volume  "postgres_data"      (nếu chưa có)
    ├─▶ 3. Tạo container "db"       ──────▶ gắn vào app-net, hostname = "db"
    ├─▶ 4. Tạo container "backend"  ──────▶ gắn vào app-net, hostname = "backend"
    ├─▶ 5. Tạo container "frontend" ──────▶ gắn vào app-net
    └─▶ 6. Tạo container "nginx"    ──────▶ gắn vào app-net
✅ Vì sao DB_HOST=db hoạt động được? Tên service trong docker-compose.yml chính là hostname trong Docker network. Docker có DNS nội bộ tự resolve tên đó thành IP container tương ứng — bạn không cần biết IP thật.

2. Kiến trúc tổng thể của project

Project này gồm 4 service chạy trong Docker, kết nối qua một mạng nội bộ app-net:

Internet (browser) │ ▼ port 80 / 443 ┌────────────────┐ │ Nginx │ ← "cổng chính" — phân luồng request │ (reverse │ │ proxy) │ └───────┬────────┘ │ ┌───────┴──────────────────────┐ │ app-net (Docker network) │ │ │ │ ┌─────────────┐ ┌──────────────────────┐ │ │ │ Frontend │ │ Backend │ │ │ │ (React + │ │ (Node.js / Express) │ │ │ │ Nginx) │ │ port 5000 │ │ │ └─────────────┘ └──────────┬────────────┘ │ │ │ │ │ ┌──────────▼────────────┐ │ │ │ PostgreSQL DB │ │ │ │ port 5432 │ │ │ └───────────────────────┘ │ └──────────────────────────────────────────────┘

Tại sao lại có 2 Nginx?

  • Nginx trong Frontend container: Chỉ phục vụ file tĩnh (HTML/CSS/JS) của React
  • Nginx service bên ngoài: Đóng vai "cổng bảo vệ" — nhận request từ internet, quyết định chuyển đến frontend hay backend

3. Dockerfile — Cách đóng gói ứng dụng

Dockerfile là file chứa các lệnh để Docker xây dựng Image. Đọc từ trên xuống dưới, mỗi dòng tạo ra một "layer" (lớp) của Image.

3.1 Multi-stage Build là gì?

Cả 2 Dockerfile trong project đều dùng kỹ thuật multi-stage build: build code ở stage 1 (có đầy đủ dev tools), rồi chỉ copy kết quả sang stage 2 (nhỏ gọn hơn nhiều).

Stage 1 (builder) Stage 2 (production) ┌─────────────────────┐ ┌──────────────────────┐ │ node:20-alpine │ │ node:20-alpine (nhỏ) │ │ npm install │ │ chỉ chứa: │ │ npm run build │───────▶│ - /app/dist │ │ (tạo ra /app/dist) │ copy │ - node_modules prod │ │ │ │ - không có src/ │ └─────────────────────┘ └──────────────────────┘ ~800MB ~180MB ✓ nhẹ hơn 4x

3.2 Backend Dockerfile — Giải thích từng dòng

# ═══ STAGE 1: Build ═══
FROM node:20-alpine AS builder
# Dùng Node 20, alpine = bản Linux tối giản (~5MB, tiết kiệm dung lượng)
# "AS builder" đặt tên stage này để stage sau tham chiếu

WORKDIR /app
# Mọi lệnh sau đây chạy trong thư mục /app bên trong container

COPY package*.json ./
# Copy package.json + package-lock.json VÀO TRƯỚC (trick tối ưu cache)
# Nếu package.json không đổi, Docker dùng cache — npm install chạy lại nhanh hơn

RUN npm ci
# npm ci = cài đúng phiên bản trong lock file (khác npm install có thể update)

COPY . .
# Copy toàn bộ source code vào /app

RUN npm run build
# Compile TypeScript → JavaScript vào thư mục /app/dist

# ═══ STAGE 2: Production image ═══
FROM node:20-alpine AS production
# Bắt đầu một Image HOÀN TOÀN MỚI — không có source code, không có dev tools

RUN apk add --no-cache curl dumb-init
# curl: dùng trong HEALTHCHECK để kiểm tra server còn sống không
# dumb-init: xử lý signal đúng cách (Ctrl+C, docker stop…)

RUN addgroup -g 1001 nodejs && adduser -S -u 1001 -G nodejs nodejs
# Tạo user "nodejs" KHÔNG phải root — bảo mật: nếu bị hack, attacker không có quyền root

WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
# --omit=dev = bỏ qua devDependencies (jest, nodemon…) — Image nhỏ hơn

COPY --from=builder --chown=nodejs:nodejs /app/dist ./dist
# Lấy thư mục /app/dist từ stage "builder" copy sang đây
# --chown=nodejs:nodejs: đổi chủ sở hữu file sang user nodejs

USER nodejs
# Từ đây mọi lệnh chạy với quyền user nodejs (không phải root)

EXPOSE 5000
# Khai báo container lắng nghe port 5000 (chỉ là metadata, không mở port thật)

HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD curl -f http://localhost:5000/api/health || exit 1
# Docker tự động gọi URL này mỗi 30s để biết container còn hoạt động không
# Nếu fail 3 lần liên tiếp → container bị đánh dấu "unhealthy"

ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/index.js"]
# Lệnh khởi động: dumb-init node dist/index.js

3.3 Frontend Dockerfile — Giải thích từng dòng

# ═══ STAGE 1: Build React ═══
FROM node:20-slim AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install --ignore-optional

COPY . .

ARG VITE_API_URL
ENV VITE_API_URL=$VITE_API_URL
# ARG: nhận tham số từ bên ngoài lúc build (docker build --build-arg VITE_API_URL=...)
# ENV: biến môi trường trong container — Vite sẽ nhúng giá trị này vào bundle JS
# QUAN TRỌNG: VITE_ prefix → Vite mới đưa vào bundle (bảo mật: không dùng cho secret)

RUN npm run build
# Tạo ra /app/dist với index.html + các file JS/CSS đã bundle

# ═══ STAGE 2: Serve bằng Nginx ═══
FROM nginx:1.25-alpine AS production
# Dùng Nginx để serve file tĩnh — nhẹ hơn chạy Node để serve

COPY nginx.conf /etc/nginx/conf.d/default.conf
# Dùng config Nginx tùy chỉnh của mình (xem mục 5)

RUN rm -rf /usr/share/nginx/html/*
COPY --from=builder /app/dist /usr/share/nginx/html
# Copy file build React vào thư mục Nginx serve

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
# "daemon off;" = Nginx chạy foreground (không chạy ngầm)
# Docker yêu cầu process chính phải chạy foreground để biết container còn sống

4. Docker Compose — Chạy nhiều container cùng lúc

Thay vì gõ lệnh docker run dài dòng cho từng container, Docker Compose cho phép định nghĩa tất cả trong file YAML và bật/tắt một lệnh.

4.1 Giải thích docker-compose.yml (môi trường dev)

services:

  # ─── PostgreSQL ───────────────────────────────────────
  db:
    image: postgres:15-alpine      # Pull image từ Docker Hub — không cần build
    container_name: myapp-db       # Tên cố định (thay vì tên ngẫu nhiên)
    restart: unless-stopped        # Tự khởi động lại nếu crash (trừ khi tắt thủ công)
    env_file: ./backend/.env       # Đọc biến môi trường từ file .env
    environment:
      POSTGRES_DB:       ${DB_NAME}    # ${} = đọc từ .env hoặc shell
      POSTGRES_USER:     ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      # postgres_data = volume có tên (Docker quản lý)
      # /var/lib/postgresql/data = nơi Postgres lưu dữ liệu trong container
      # Khi container bị xóa, dữ liệu VẪN CÒN trong volume
    ports:
      - "5433:5432"   # host:container — dùng 5433 tránh conflict với Postgres local
    networks: [app-net]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s    # Kiểm tra mỗi 10 giây
      timeout: 5s      # Chờ tối đa 5 giây
      retries: 5       # Thử lại 5 lần trước khi báo unhealthy

  # ─── Node.js Backend ──────────────────────────────────
  backend:
    build:
      context: ./backend     # Thư mục chứa Dockerfile và source code
      dockerfile: Dockerfile  # Tên file Dockerfile
    environment:
      DB_HOST: db      # "db" = tên service phía trên = hostname trong Docker network
      DB_PORT: 5432    # Port nội bộ (không phải 5433 — đó là port ra ngoài host)
      NODE_ENV: development
    ports:
      - "5000:5000"
    depends_on:
      db:
        condition: service_healthy   # Chờ db healthy TRƯỚC khi khởi động backend
    volumes:
      - ./backend/src:/app/src   # Bind mount: sửa code local → ngay lập tức phản ánh vào container

  # ─── React Frontend ───────────────────────────────────
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    depends_on: [backend]   # Khởi động sau backend
    networks: [app-net]
    # Không expose port ra ngoài — chỉ Nginx mới nhận request

  # ─── Nginx reverse proxy ──────────────────────────────
  nginx:
    image: nginx:1.25-alpine   # Không build — dùng image có sẵn
    ports:
      - "80:80"   # Chỉ Nginx mới expose ra internet (port 80)
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      # :ro = read-only, container không sửa được file config
    depends_on: [frontend, backend]

volumes:
  postgres_data:   # Khai báo named volume — Docker quản lý, không bị xóa theo container

networks:
  app-net:
    driver: bridge   # Bridge network: các container cùng network nói chuyện được với nhau

5. Nginx — Reverse Proxy là gì?

5.1 Khái niệm Reverse Proxy

Client (browser) │ │ GET /api/todos │ GET / ▼ ┌────────────────────────────────────────────┐ │ Nginx (port 80) │ │ │ │ /api/* ──────────────────▶ Backend:5000 │ │ /* (còn lại) ────────────▶ Frontend:80 │ └────────────────────────────────────────────┘

Nginx đứng giữa internet và các service nội bộ. Client không biết Backend đang ở đâu — họ chỉ thấy Nginx. Điều này giúp:

  • Tập trung SSL (HTTPS) tại một chỗ
  • Load balancing (phân tải giữa nhiều instance)
  • Cache, compression
  • Ẩn cổng nội bộ (bảo mật)

5.2 nginx.conf trong Frontend container

server {
    listen 80;
    root /usr/share/nginx/html;   # Thư mục chứa file React build
    index index.html;

    # Bật nén gzip — file JS 300KB → 80KB khi truyền qua mạng
    gzip on;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;

    # Cache file static 1 năm — Vite đã hash tên file (main.a1b2c3d4.js)
    # Khi code thay đổi, tên file đổi → browser tự tải file mới
    location ~* \.(js|css|png|jpg|jpeg|svg|ico|woff2?)$ {
        expires 1y;
        add_header Cache-Control "public,immutable";
        access_log off;
    }

    # SPA routing: React Router xử lý URL bằng JS
    # Khi user vào /about, không có file /about trên server
    # try_files thử tìm file đó → không có → trả index.html → React Router xử lý
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Chặn truy cập file ẩn: .env, .git, .htaccess…
    location ~ /\. { deny all; }
}
⚠️ SPA Routing — Lỗi thường gặp Nếu không có dòng try_files $uri $uri/ /index.html, user vào trực tiếp /about (F5 hoặc copy URL) sẽ nhận lỗi 404 từ Nginx vì file /about không tồn tại trên disk.

6. Biến môi trường (.env)

File .env chứa thông tin nhạy cảm (mật khẩu DB, API key…). Không bao giờ commit file .env lên Git!

Cấu trúc file .env (theo .env.example)

# Database
DB_NAME=myapp
DB_USER=admin
DB_PASSWORD=changeme_in_production   # Đổi khi deploy thật!

# Backend

9. CI/CD với GitHub Actions

9.1 CI/CD là gì?

  • CI (Continuous Integration): Mỗi lần push code → tự động test, build
  • CD (Continuous Deployment): Sau khi CI pass → tự động deploy lên server

Kết quả: Code mới lên main → 5-10 phút sau đã live trên production — không cần thao tác thủ công.

9.2 File GitHub Actions (production-ready)

File .github/workflows/deploy.yml — tách thành 2 job độc lập:

JobLàm gì
buildBuild Docker image → push lên ECR
deployCopy config → tạo .env → pull image → restart
name: Build & Deploy

on:
  push:
    branches: [main]

env:
  AWS_REGION: ap-southeast-1
  ECR_REGISTRY: ${{ secrets.ECR_REGISTRY }}

jobs:

  # ── JOB 1: Build ──────────────────────────────────────────
  build:
    name: Build & Push to ECR
    runs-on: ubuntu-latest
    outputs:
      image_tag: ${{ steps.tag.outputs.tag }}   # truyền tag sang job deploy

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id:     ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region:            ${{ env.AWS_REGION }}

      - name: Login to ECR
        uses: aws-actions/amazon-ecr-login@v2

      - name: Set image tag (git short SHA)
        id: tag
        run: echo "tag=${GITHUB_SHA::7}" >> $GITHUB_OUTPUT
        # tag = 7 ký tự đầu của commit SHA → ví dụ: "a1b2c3d"
        # Lợi ích: biết chính xác commit nào đang chạy, rollback dễ dàng

      - name: Build & push backend
        run: |
          docker build \
            -t $ECR_REGISTRY/myapp-backend:${{ steps.tag.outputs.tag }} \
            ./backend
          docker push $ECR_REGISTRY/myapp-backend:${{ steps.tag.outputs.tag }}
          # Tag thêm "latest" để tiện dùng thủ công
          docker tag  $ECR_REGISTRY/myapp-backend:${{ steps.tag.outputs.tag }} \
                      $ECR_REGISTRY/myapp-backend:latest
          docker push $ECR_REGISTRY/myapp-backend:latest

      - name: Build & push frontend
        run: |
          docker build \
            --build-arg VITE_API_URL=${{ secrets.VITE_API_URL }} \
            -t $ECR_REGISTRY/myapp-frontend:${{ steps.tag.outputs.tag }} \
            ./frontend
          docker push $ECR_REGISTRY/myapp-frontend:${{ steps.tag.outputs.tag }}
          docker tag  $ECR_REGISTRY/myapp-frontend:${{ steps.tag.outputs.tag }} \
                      $ECR_REGISTRY/myapp-frontend:latest
          docker push $ECR_REGISTRY/myapp-frontend:latest

  # ── JOB 2: Deploy ─────────────────────────────────────────
  deploy:
    name: Deploy to EC2
    runs-on: ubuntu-latest
    needs: build   # chỉ chạy khi job build thành công

    steps:
      - uses: actions/checkout@v4

      # Copy file config (không nhạy cảm) lên EC2 qua SCP
      # EC2 không cần clone repo — chỉ cần 2 file này
      - name: Copy config files to EC2
        uses: appleboy/scp-action@v0.1.7
        with:
          host:             ${{ secrets.EC2_HOST }}
          username:         ubuntu
          key:              ${{ secrets.EC2_SSH_KEY }}
          source:           "docker-compose.prod.yml,nginx/default.conf"
          target:           ~/app
          strip_components: 0

      # SSH vào EC2: tạo .env từ Secrets → login ECR → deploy
      - name: Deploy
        uses: appleboy/ssh-action@v1
        env:
          ECR_REGISTRY: ${{ secrets.ECR_REGISTRY }}
          IMAGE_TAG:    ${{ needs.build.outputs.image_tag }}
          DB_NAME:      ${{ secrets.DB_NAME }}
          DB_USER:      ${{ secrets.DB_USER }}
          DB_PASSWORD:  ${{ secrets.DB_PASSWORD }}
        with:
          host:     ${{ secrets.EC2_HOST }}
          username: ubuntu
          key:      ${{ secrets.EC2_SSH_KEY }}
          envs:     ECR_REGISTRY,IMAGE_TAG,DB_NAME,DB_USER,DB_PASSWORD
          script: |
            set -e
            cd ~/app

            # Tạo .env từ GitHub Secrets — không lưu trên git, không có trên server
            mkdir -p backend
            cat > backend/.env << EOF
            DB_NAME=${DB_NAME}
            DB_USER=${DB_USER}
            DB_PASSWORD=${DB_PASSWORD}
            PORT=5000
            NODE_ENV=production
            EOF

            # Login ECR từ EC2
            aws ecr get-login-password --region ap-southeast-1 | \
              docker login --username AWS --password-stdin ${ECR_REGISTRY}

            # Pull images mới
            ECR_REGISTRY=${ECR_REGISTRY} IMAGE_TAG=${IMAGE_TAG} \
              docker compose -f docker-compose.prod.yml pull

            # Restart với images mới
            ECR_REGISTRY=${ECR_REGISTRY} IMAGE_TAG=${IMAGE_TAG} \
              docker compose -f docker-compose.prod.yml up -d

            # Dọn images cũ — tiết kiệm disk EC2
            docker image prune -f

            echo "Deployed: ${IMAGE_TAG}"

12. Câu hỏi thường gặp (FAQ)

❓ Sự khác biệt giữa docker compose up và docker compose up --build?

up dùng Image đã có sẵn (từ lần build trước). up --build buộc build lại Image từ Dockerfile. Dùng --build khi bạn sửa Dockerfile hoặc thêm dependency mới.

❓ Tại sao backend dùng DB_HOST là "db" chứ không phải "localhost"?

Trong Docker network, mỗi service được truy cập bằng tên service (không phải localhost). Backend container và DB container là 2 "máy" khác nhau — muốn kết nối phải dùng hostname là tên service trong compose: db.

❓ Port 5433 vs 5432 — dùng khi nào?

  • 5432: Port Postgres bên trong Docker network (backend dùng cái này)
  • 5433: Port trên máy host (bạn dùng pgAdmin/DBeaver kết nối DB để debug)

Rule: host_port:container_port → 5433:5432

❓ restart: unless-stopped vs restart: always?

  • unless-stopped: Tự restart nếu crash, KHÔNG restart nếu bạn docker stop thủ công
  • always: Luôn luôn restart, kể cả sau khi reboot server hoặc docker stop
  • Production dùng always — server reboot sau update vẫn tự bật lại

❓ Volume bind mount vs named volume?

  • Bind mount (./src:/app/src): Link thẳng thư mục trên host vào container. Dùng khi dev để hot-reload.
  • Named volume (postgres_data:/var/lib/postgresql/data): Docker quản lý, không phụ thuộc đường dẫn host. Dùng cho dữ liệu cần lưu bền vững.

❓ Khi nào cần rebuild Image?

  • Thêm/xóa package trong package.json
  • Sửa Dockerfile
  • Thêm file config mới cần COPY vào Image

Chỉ sửa code TypeScript/JavaScript? Không cần rebuild nếu đang dev với bind mount!

❓ Image tag "latest" có vấn đề gì?

:latest không đảm bảo là phiên bản mới nhất — chỉ là tên tag mặc định. Trong production, dùng tag cụ thể (git SHA: abc1234) để biết chính xác phiên bản nào đang chạy và rollback dễ dàng bằng cách đổi tag.

❓ Cách rollback khi deploy lỗi?

# Trên EC2, đổi IMAGE_TAG về commit SHA cũ
export IMAGE_TAG=abc1234   # tag của phiên bản tốt
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
