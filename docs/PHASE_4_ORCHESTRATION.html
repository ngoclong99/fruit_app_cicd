1. Tại sao Container Orchestration

Vấn đề với ASG (Phase 3)

  • Vẫn phải nghĩ về "EC2" — AMI, instance type, user-data, ssh keys, security patches
  • Tốn tiền cho cả OS overhead (kernel, systemd, sshd...) — chiếm 20-30% RAM/CPU không liên quan app
  • Scale theo EC2 (whole-VM granularity) — muốn 1.5 EC2 → phải trả 2 EC2
  • Deploy là rolling SSH — phức tạp, dễ lỗi

6. Module A — ECR Lifecycle Policy

📌 Tại sao làm trước module khác ECR lifecycle là module cheapest + safest để bắt đầu: FREE, idempotent, không phá gì hiện có. Đáng làm ngay vì tiết kiệm tiền thật (ECR storage $0.10/GB/tháng tích lũy nhanh nếu CI build mỗi commit).

Vấn đề thực tế

Mỗi lần CI build push 1 image mới vào ECR. Sau 6 tháng dev:

ResourceSố lượngCost
Image trong myapp-backend~150 (1-2 deploy/ngày × 90 ngày)~150 × 200MB = 30GB = $3/tháng
Image trong myapp-frontend~150~150 × 50MB = 7.5GB = $0.75/tháng
Untagged orphan layers~50 (CI fail giữa chừng)~$1/tháng
Tổng tích lũy—~$5/tháng và tăng dần

Lifecycle policy giải quyết

Policy = rule JSON tự xóa image theo quy tắc. ECR chạy policy ~mỗi 24h (không real-time). Khi policy match image → xóa vĩnh viễn.

A0 Discover — check ECR repos hiện có (read-only)

AWS CLI
# 1. List tat ca repos
aws ecr describe-repositories --region ap-southeast-1 `
  --query "repositories[].{Name:repositoryName,URI:repositoryUri,Created:createdAt}" `
  --output table

# 2. Dem image trong moi repo
foreach ($repo in @("myapp-backend", "myapp-frontend")) {
  $count = aws ecr describe-images --region ap-southeast-1 --repository-name $repo `
    --query "length(imageDetails)" --output text
  Write-Host "$repo : $count images"
}

# 3. Tinh tong storage
aws ecr describe-images --region ap-southeast-1 --repository-name myapp-backend `
  --query "sum(imageDetails[].imageSizeInBytes) / \`1048576\`" --output text
# Output: tong MB

# 4. Check policy hien tai (neu co)
aws ecr get-lifecycle-policy --region ap-southeast-1 --repository-name myapp-backend 2>$null
# Neu chua co se bao "LifecyclePolicyNotFoundException"

Ghi lại 2 số: số image hiện tại + tổng MB → so sánh sau khi apply policy.

A1 Tạo lifecycle policy đơn giản (giữ 10 image gần nhất)

AWS Console UIAWS CLI

UI walkthrough

  1. Console → ECR → Private registry → Repositories → myapp-backend
  2. Tab Lifecycle Policy (nếu không thấy: scroll qua phải)
  3. Click Create rule
  4. Điền form:
    • Rule priority: 1 (lower number = higher priority)
    • Rule description: Keep last 10 images, delete rest
    • Image status: Any (cả tagged và untagged)
    • Match criteria: Image count more than
    • Count: 10
    • Rule action: expire
  5. Save and test — quan trọng! Test mode show image nào sẽ bị xóa, KHÔNG xóa thật
  6. Verify danh sách image sẽ xóa → nếu OK, click Save để apply
  7. Lặp lại cho myapp-frontend

CLI

# 1. Tao policy JSON
$policy = @{
  rules = @(
    @{
      rulePriority = 1
      description  = "Keep last 10 images, delete rest"
      selection    = @{
        tagStatus   = "any"
        countType   = "imageCountMoreThan"
        countNumber = 10
      }
      action = @{ type = "expire" }
    }
  )
} | ConvertTo-Json -Depth 10

# 2. Ghi ra file tam
$tmpFile = [System.IO.Path]::GetTempFileName()
[System.IO.File]::WriteAllText($tmpFile, $policy)

# 3. Apply cho 2 repos
foreach ($repo in @("myapp-backend", "myapp-frontend")) {
  aws ecr put-lifecycle-policy --region ap-southeast-1 `
    --repository-name $repo `
    --lifecycle-policy-text "file://$tmpFile"
  Write-Host "Policy applied to $repo" -ForegroundColor Green
}

# 4. Cleanup tmp file
Remove-Item $tmpFile -Force

A2 Tạo policy phức tạp (khuyến nghị cho production)

Rule đơn ở A1 đủ cho demo. Production nên có policy phân biệt tagged vs untagged:

{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Giu 10 image moi nhat co tag main-*",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["main-"],
        "countType": "imageCountMoreThan",
        "countNumber": 10
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Giu 5 image moi nhat co tag staging-*",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["staging-"],
        "countType": "imageCountMoreThan",
        "countNumber": 5
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 3,
      "description": "Xoa untagged sau 7 ngay (orphan tu CI fail)",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": { "type": "expire" }
    }
  ]
}
ℹ️ Thứ tự rule quan trọng Rule chạy theo priority tăng dần. Image match rule SỚM thì rule sau không apply. Vì vậy nên đặt rule "giữ" trước rule "xóa" — tránh accident xóa image vẫn đang dùng.

A3 Test policy KHÔNG xóa thật (preview mode)

ECR có preview API cho test policy:

} while ($status -eq "IN_PROGRESS")

# 3. Xem ket qua
aws ecr get-lifecycle-policy-preview --region ap-southeast-1 `
  --repository-name myapp-backend `

  --output table

7. Module B — CloudWatch Logs centralization

Tại sao

Hiện tại logs container ở trên EC2 (docker logs). Khi EC2 chết → mất log. Khi nhiều EC2 → khó tổng hợp.

CloudWatch Logs:

  • Centralize log từ mọi container/instance/service
  • Search bằng CloudWatch Logs Insights (SQL-like)
  • Có retention (auto xóa log cũ)
  • Alarms based on log patterns (vd 5xx errors > threshold)

B1 Tạo Log Group (UI)

AWS Console UI
  1. Console → CloudWatch → Logs → Log groups → Create log group
  2. Log group name: /ecs/myapp
  3. Retention setting: 7 days (demo) hoặc 30 days (prod). Mặc định "Never expire" sẽ phình mãi.
  4. Create

B2 Tạo Log Group (CLI)

AWS CLI
aws logs create-log-group --log-group-name /ecs/myapp --region ap-southeast-1
aws logs put-retention-policy --log-group-name /ecs/myapp --retention-in-days 7 --region ap-southeast-1

Log driver cho ECS task

Sẽ cấu hình trong Task Definition (Module D):

"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group":         "/ecs/myapp",
    "awslogs-region":        "ap-southeast-1",
    "awslogs-stream-prefix": "backend"
  }
}

Tip: CloudWatch Logs Insights query

Sau khi log đổ vào CW, vào CloudWatch → Logs Insights và query:

# Tim tat ca error gan day
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 50

# Dem 5xx response theo phut
fields @timestamp, @message
| parse @message '"statusCode":*' as statusCode
| filter statusCode >= 500
| stats count() by bin(1m)
💡 Cost CloudWatch Logs $0.50/GB ingestion + $0.03/GB stored. Demo <1GB/tháng → ~$0.50/tháng. Đặt retention 7 ngày để tránh phình.

9. Module D — Task Definition

Task Definition là gì

JSON spec mô tả cách chạy 1 task:

  • Container nào (image, command, environment)
  • CPU + RAM phân bổ
  • Networking mode (Fargate bắt buộc awsvpc)
  • IAM role (task role + execution role)
  • Volume mounts (nếu có)
  • Log config

D1 Viết Task Definition (file JSON)

Tạo file ecs/task-definition.json:

{
  "family": "myapp-production",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu":    "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::529568113348:role/ecsTaskExecutionRole",
  "taskRoleArn":      "arn:aws:iam::529568113348:role/myapp-ecs-task-role",
  "containerDefinitions": [
    {
      "name": "backend",
      "image": "<ECR_REGISTRY>/myapp-backend:main-latest",
      "essential": true,
      "portMappings": [{ "containerPort": 5000, "protocol": "tcp" }],
      "secrets": [
        { "name": "DB_PASSWORD", "valueFrom": "arn:aws:ssm:ap-southeast-1:529568113348:parameter/myapp/production/DB_PASSWORD" },

      "environment": [
        { "name": "NODE_ENV",  "value": "production" },

        "logDriver": "awslogs",

          "awslogs-group":         "/ecs/myapp",

        }
      },
      "healthCheck": {

      }
    },
    {
      "name": "frontend",
      "image": "<ECR_REGISTRY>/myapp-frontend:main-latest",
      "essential": true,

11. Module F — Blue/Green Deploy với CodeDeploy

Blue/Green concept

Truoc khi deploy: ALB Listener :443 ────► TG-Blue (current task v1) ────► task v1 TG-Green (empty) Trong deploy: ALB Listener :443 ────► TG-Blue (current task v1) ────► task v1 TG-Green ────► task v2 (new revision) (run "smoke test") Cutover: ALB Listener :443 ────► TG-Green ◄── traffic shift 100% TG-Blue ────► task v1 (waiting to drain) Done: ALB Listener :443 ────► TG-Green ────► task v2 TG-Blue (empty) [task v1 terminated]

Lợi ích vs rolling:

  • Test version mới (smoke test) trước khi shift traffic
  • Rollback <1 phút bằng cách shift về Blue
  • Không có thời gian "mixed" (rolling = vừa v1 vừa v2 cùng phục vụ)

15. Troubleshooting

Task không start (PENDING mãi)

  • Subnet không có internet (cần NAT hoặc public IP để pull ECR)
  • Task Execution Role không có quyền pull ECR / ghi CloudWatch
  • Image tag không tồn tại trong ECR
  • Check CloudWatch event stream: aws ecs describe-tasks ... --query "tasks[0].stoppedReason"

Target group target unhealthy

  • Health check path sai (Fargate task không có nginx? hoặc port khác)
  • Security group: ECS SG chưa allow port từ ALB SG
  • Container chưa start xong → tăng health check grace period

Secrets từ SSM không inject

  • Task Execution Role thiếu ssm:GetParameters + kms:Decrypt (nếu SecureString)
  • Parameter ARN sai region

Blue/Green deploy stuck

  • CodeDeploy chờ approval (nếu chọn manual)
  • Test listener target unhealthy → traffic không shift

Part 2 — Serverless (Lambda + API Gateway + EventBridge)

Phần trên về ECS Fargate là compute paradigm thứ 2 (sau EC2). Phần này về paradigm thứ 3 — Serverless: bạn viết function, AWS lo TẤT CẢ phần dưới (OS, runtime, scaling, networking).

a. Tại sao Lambda — paradigm thứ 3

┌─────────────────────────────────────────────────────────┐ │ PARADIGM 1 — EC2 (Phase 1-3) │ │ Ban quan ly: OS, patch, scale, monitor, restart │ │ AWS quan ly: phan cung │ │ Billing: per HOUR EC2 chay (du khong xai) │ ├─────────────────────────────────────────────────────────┤ │ PARADIGM 2 — Container (Fargate, Phase 4 Part 1) │ │ Ban quan ly: container image + task definition │ │ AWS quan ly: OS, kernel, container runtime, scaling │ │ Billing: per SECOND task chay │ ├─────────────────────────────────────────────────────────┤ │ PARADIGM 3 — Serverless (Lambda, Phase 4 Part 2) │ │ Ban quan ly: CHI function code (handler) │ │ AWS quan ly: OS, runtime, container, scaling, network │ │ Billing: per REQUEST + ms execution time │ │ Free tier: 1M request + 400,000 GB-second/month │ └─────────────────────────────────────────────────────────┘

Use cases Lambda hay nhất

Use caseVì sao Lambda phù hợp
Cron job (scheduled task)Chạy 1 phút/ngày → EC2 lãng phí 23h59'. Lambda + EventBridge cost ~$0
Image processing khi upload S3Event-driven: S3 trigger Lambda tự động khi có file mới
Webhook nhận event từ Stripe/GitHubKhoản traffic ít, không đáng dựng server riêng
REST API có ít request1000 req/ngày = $0. Server EC2 = $7-15/tháng
Stream processing (Kinesis, DynamoDB streams)Auto scale theo throughput
Auto cleanup (tự xóa file cũ, EC2 cũ)Trigger by EventBridge schedule

Khi nào KHÔNG dùng Lambda

  • Workload chạy liên tục 24/7: Lambda đắt hơn EC2 nếu function chạy hàng giờ liên tục
  • Cần persistent state trong RAM: Lambda stateless, mỗi invocation memory reset (trừ khi dùng Lambda extension)
  • WebSocket connections lâu: Lambda max 15 phút mỗi invocation. Dùng API Gateway WebSocket + connection table
  • Long-running batch job: 15 phút limit → dùng Step Functions / ECS task / Batch
  • Cold start critical: First invocation sau idle có 200ms-2s cold start delay

import boto3

ec2 = boto3.client("ec2", region_name="ap-southeast-1")
ecr = boto3.client("ecr", region_name="ap-southeast-1")

def lambda_handler(event, context):
    # 1. Terminate EC2 voi tag myapp-ec2
    instances = ec2.describe_instances(
        Filters=[
            {"Name": "tag:Name", "Values": ["myapp-ec2"]},
            {"Name": "instance-state-name", "Values": ["running", "pending"]}
        ]
    )
    ids = [i["InstanceId"] for r in instances["Reservations"] for i in r["Instances"]]
    if ids:
        ec2.terminate_instances(InstanceIds=ids)

    # 2. Xoa ECR repos de tiet kiem $0.10/GB/thang
    for repo in ["myapp-backend", "myapp-frontend"]:
        try:
            ecr.delete_repository(repositoryName=repo, force=True)
        except ecr.exceptions.RepositoryNotFoundException:
            pass

    return {"terminated": ids, "ecr_cleared": True}

  • DynamoDB: NoSQL key-value/document, milli-second latency at any scale
  • SQS: queue async, decouple producer/consumer
  • SNS + EventBridge: pub/sub + event bus cho event-driven architecture

Bonus: Phase 5 sẽ kết hợp với Lambda của Phase 4 — Lambda sẽ là consumer của SQS, subscriber của SNS, processor của DynamoDB Streams.
