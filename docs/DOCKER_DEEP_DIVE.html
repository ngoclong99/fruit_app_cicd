Part 1 — Foundation

a. Vấn đề trước Docker — "works on my machine"

Trước Docker (~2013), deploy một app phức tạp thường gặp các vấn đề sau:

Vấn đềTình huống thực tế
Dev khác ProdDev viết app trên Mac với Node 18, server prod chạy Ubuntu 18 với Node 14 — code fail vì syntax mới
Dependency conflictApp A cần Python 3.7, app B cần Python 3.10 — cùng 1 server không thể có 2 version Python tách biệt sạch
Cài thủ côngSetup server mới = đọc wiki 20 trang, chạy 50 lệnh, dễ bỏ sót 1 bước

Resource isolation kémApp leak memory → server đơ → app khác trên cùng server cũng đơ

"works on my machine" — câu nói legendary

Developer kêu "code chạy ổn trên máy tôi mà!" → DevOps phải debug tại sao prod khác → mất giờ. Docker giải quyết bằng cách đóng gói cả môi trường vào trong "image": OS layer, lib, runtime, code. Image chạy ở đâu cũng giống nhau.

💡 Tóm gọn vấn đề Docker = "shipping container của software". Trước Docker, mỗi app vận chuyển kèm cả 1 "kho" (server). Có Docker, app + môi trường được nén vào "thùng" chuẩn, chuyển đi đâu cũng được.

b. Container vs Virtual Machine

Container thường bị nhầm với VM. Cả hai đều "đóng gói app", nhưng cơ chế khác hoàn toàn.

Container là VM nhẹ không?

Không. Container không phải VM nhẹ. Container không có OS riêng — chỉ là 1 nhóm process được isolation qua 2 cơ chế của Linux kernel:

  • Namespaces: cô lập view của process — process A không nhìn thấy process B (PID namespace), không thấy network của B (net namespace), không truy cập file của B (mount namespace)...
  • cgroups: giới hạn tài nguyên — container A chỉ được dùng 0.5 CPU + 512MB RAM

Nghĩa là khi bạn chạy docker run alpine ls, host kernel chạy lệnh ls bình thường, nhưng "đặt" nó vào 1 cái "hộp" có namespace + cgroup riêng. Process chỉ thấy được những gì bên trong hộp.

ℹ️ Trên Mac/Windows thì sao? macOS / Windows kernel không có Linux namespaces/cgroups → Docker Desktop chạy 1 VM Linux nhỏ (qua HyperKit / WSL2 / Hyper-V) làm host cho container. Vì vậy trên Mac/Windows, container ngầm chạy trong VM. Trên Linux native, không có VM.

Ví dụ end-to-end

# 1. Viet Dockerfile (source)
echo "FROM nginx:alpine" > Dockerfile

# 2. Build thanh image (compile)
docker build -t myapp:v1 .
# myapp:v1 -- tag cua image

# 3. Run image thanh container (instantiate)
docker run -d --name myapp-1 myapp:v1
# Container voi ID rieng, dang chay

# 4. Push image len registry (publish)
docker tag myapp:v1 myuser/myapp:v1
docker push myuser/myapp:v1

# 5. May khac pull va run (reuse)
docker pull myuser/myapp:v1
docker run -d myuser/myapp:v1

d. Kiến trúc Docker — client / daemon / registry

┌───────────────────┐ Unix socket / ┌──────────────────────┐ │ docker CLI │ /var/run/docker.sock │ Docker daemon │ │ (client) │ ───────────────────► │ (dockerd) │ │ │ │ │ │ docker build │ HTTP API: │ - Build images │ │ docker run │ - POST /containers/ │ - Manage container │ │ docker ps │ - GET /images/ │ lifecycle │ │ docker logs │ - DELETE /networks/ │ - Network/volume │ └───────────────────┘ │ - Talk to OS: │ │ namespaces, │ │ cgroups, layers │ └────────┬─────────────┘ │ │ HTTPS pull/push ▼ ┌──────────────────────┐ │ Registry │ │ (Docker Hub / ECR) │ └──────────────────────┘

3 thành phần

  • Docker CLI (docker): công cụ command-line bạn gõ. Không tự làm gì — chỉ gửi HTTP request đến daemon.
  • Docker daemon (dockerd): process chạy nền, làm hết công việc thật — build image, start/stop container, manage network, gọi kernel.
  • Registry: server lưu trữ image. Public default: hub.docker.com. Private cho team: ECR, GHCR, GitLab Registry, Harbor (self-hosted).
ℹ️ Vì sao daemon chạy as root? Docker daemon cần quyền tạo namespace, cgroup, mount filesystem... → cần root. Đây là lý do thêm user vào group docker = thực chất cho user đó quyền root gián tiếp. Cẩn thận với nhóm docker trên prod.

c. Image layers — sự thật bên trong

Image KHÔNG phải 1 file đơn — nó là chuỗi layer xếp chồng. Mỗi instruction trong Dockerfile tạo 1 layer.

Dockerfile: FROM node:20-alpine ─► Layer 1: base image (~150 MB) WORKDIR /app ─► Layer 2: tao /app (~0 byte) COPY package*.json ./ ─► Layer 3: them 2 file (~50 KB) RUN npm install ─► Layer 4: them node_modules (~100 MB) COPY . . ─► Layer 5: them src code (~5 MB) RUN npm run build ─► Layer 6: them dist/ (~10 MB) Image cuoi cung: ┌────────────────────────────────────┐ │ Layer 6: dist/ (read-only) │ ├────────────────────────────────────┤ │ Layer 5: src/ (read-only) │ ├────────────────────────────────────┤ │ Layer 4: node_modules (read-only) │ ├────────────────────────────────────┤ │ Layer 3: package*.json (read-only) │ ├────────────────────────────────────┤ │ Layer 2: WORKDIR /app (read-only) │ ├────────────────────────────────────┤ │ Layer 1: node:20-alpine (RO) │ └────────────────────────────────────┘ ▲ khi `docker run`: │ ┌────────────────────────────────────┐ │ Container writable layer │ ← container ghi file vao day │ (chi co o container, khong o image)│ (mat khi remove container) └────────────────────────────────────┘

LệnhState sauNote

a. 3 loại storage: bind / volume / tmpfs

Container writable layer mất khi xóa container → cần cách lưu data bền vững.

┌─────────────────────────────────────────────────────────────────┐ │ Host filesystem: │ │ │ │ /home/user/data/ ─────────┐ │ │ │ bind mount (path tu chinh) │ │ ▼ │ │ /var/lib/docker/volumes/ ┌─────────────────────┐ │ │ myvolume/ │ CONTAINER: │ │ │ _data/ ────────────│ /app/data │ │ │ volume └─────────────────────┘ │ │ (Docker quan) │ │ ▲ │ │ │ tmpfs (chi RAM, khong vao disk) │ │ (RAM) ────────────────────┘ │ └─────────────────────────────────────────────────────────────────┘
LoạiCú phápĐặc điểmUse case

Bind mount — dùng cho dev

# Mount thu muc source vao container -> nodemon hot-reload
docker run -d --name dev \
  -v /home/long/project/src:/app/src \
  myapp:dev

# Read-only mount (an toan hon)
docker run -v /etc/myconfig:/etc/myconfig:ro myapp

Named volume — dùng cho persistent

# Tao volume
docker volume create pgdata

# Dung trong container
docker run -d --name pg \
  -v pgdata:/var/lib/postgresql/data \
  postgres:15

# Container xoa, data van con
docker rm -f pg

# Run container moi, attach lai volume -> data van do
docker run -d --name pg2 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:15

# Liet ke volume
docker volume ls

# Xem chi tiet (de biet location tren host)
docker volume inspect pgdata
# Mountpoint: /var/lib/docker/volumes/pgdata/_data

# Xoa volume (CAN THAN -- mat data)
docker volume rm pgdata

tmpfs — secrets / hot cache

docker run -d \
  --tmpfs /tmp/cache:size=100m,mode=1777 \
  myapp
🎯 Thực tế đi làm 90% volume bạn gặp là named volume cho DB (postgres_data, redis_data...) + bind mount cho config (./nginx.conf:/etc/nginx/conf.d/default.conf:ro). Trong dev cũng dùng bind cho source code (hot-reload). tmpfs ít gặp hơn.

# Truy cap host:8080 -> den container:80

c. DNS nội bộ — vì sao container gọi container bằng tên

CMD vs ENTRYPOINT — nguồn confusion lớn nhất

# Case 1: CMD only -- user co the OVERRIDE
CMD ["node", "app.js"]
# docker run myimg          -> node app.js
# docker run myimg sh        -> sh (override)

# Case 2: ENTRYPOINT only -- user CHI co the them arg
ENTRYPOINT ["node"]
# docker run myimg app.js   -> node app.js
# docker run myimg --version -> node --version

# Case 3: Ca hai -- ENTRYPOINT la binary chinh, CMD la default args
ENTRYPOINT ["node"]
CMD ["app.js"]
# docker run myimg          -> node app.js (CMD lam default)
# docker run myimg test.js  -> node test.js (user thay CMD)
💡 Quy tắc tốt Production thường dùng ENTRYPOINT + CMD. ENTRYPOINT = init wrapper (dumb-init/tini) để handle signal đúng. CMD = lệnh thực tế của app.

b. Layer caching — lý do COPY package.json TRƯỚC code

Docker cache layer theo thứ tự. Nếu instruction X có cache hit, các instruction TRƯỚC X cũng cache. Khi 1 instruction cache miss, mọi instruction SAU đó phải build lại.

BAD example

FROM node:20-alpine
WORKDIR /app
COPY . .                  # <-- copy ca code va package.json
RUN npm install           # <-- cache miss moi khi code thay doi!
RUN npm run build
CMD ["node", "dist/index.js"]

Vấn đề: chỉ đổi 1 dòng trong src/index.ts → COPY . . miss cache → npm install chạy lại (tốn 30s+) dù package.json không đổi.

GOOD example

FROM node:20-alpine
WORKDIR /app

# Copy package.json TRUOC -- it doi nhat
COPY package*.json ./
RUN npm install           # <-- cache se hit lien tuc neu package.json khong doi

# Code copy sau -- thay doi thuong xuyen
COPY . .
RUN npm run build

CMD ["node", "dist/index.js"]

Build lần đầu: install npm 30s. Lần sau đổi code: chỉ build từ COPY . . trở đi → 5s.

ℹ️ Quy tắc thứ tự Trong Dockerfile, sắp xếp instruction theo tần suất thay đổi tăng dần: thứ ít đổi nhất ở trên, thứ hay đổi nhất ở dưới.

Lệnh xem cache

docker build --no-cache -t myapp .   # Force rebuild moi layer
docker build --progress=plain .       # In CACHED de biet layer nao da cache

c. Multi-stage build — giảm image size 10×

Build app cần nhiều tool (compiler, build deps, source code) mà runtime không cần. Multi-stage = chạy build trong 1 stage, copy artifact ra stage khác.

Without multi-stage (BAD)

FROM node:20
WORKDIR /app
COPY . .
RUN npm install        # 500MB node_modules
RUN npm run build      # Tao ra dist/
CMD ["node", "dist/index.js"]
# Image final: ~1.5 GB (chua TypeScript, devDeps, source code...)

With multi-stage (GOOD)

# Stage 1: builder -- co full toolchain
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install                          # Cai het, ke ca devDeps
COPY . .
RUN npm run build                        # Tao dist/

# Stage 2: production -- chi co runtime
FROM node:20-alpine AS production
WORKDIR /app

COPY package*.json ./
RUN npm install --omit=dev               # CHI prod deps, khong devDeps

COPY --from=builder /app/dist ./dist     # Copy artifact tu builder

CMD ["node", "dist/index.js"]
# Image final: ~150 MB (giam 10×)
🎯 Thực tế đi làm Multi-stage luôn dùng cho mọi app non-trivial. Java/Go/Rust thậm chí giảm còn ~20MB (chỉ binary, không có JVM/Go runtime). Project bạn dùng pattern này — xem mục f.

Multi-stage build với cùng 1 base nhưng khác purpose

FROM node:20 AS dev
# Stage dev: co tools, hot-reload, debugger
WORKDIR /app
COPY . .
RUN npm install
CMD ["npm", "run", "dev"]

FROM node:20 AS builder
COPY . .
RUN npm install && npm run build

FROM node:20-alpine AS prod
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]

# Build target cu the:
# docker build --target dev -t myapp:dev .
# docker build --target prod -t myapp:prod .

d. Best practices: security, size, performance

Security

  • Non-root user: tạo user riêng (uid > 1000), USER trước CMD. Lỡ RCE thì attacker không có root trong container.
  • Image nhẹ: alpine (~5MB) hoặc distroless (~20MB, không có shell). Surface attack nhỏ.
  • Không hardcode secret: env / build-arg đều LỘ trong image layers. Dùng secret manager hoặc --secret flag của BuildKit.
  • Pin version: node:20.11.1-alpine chứ không node:latest. Reproducible build.
  • Verify checksum: download binary thì check sha256.
  • Scan image: Trivy / Docker Scout phát hiện CVE.

Size

  • Dùng alpine / distroless / scratch (cho Go binary)
  • Multi-stage build (mục c)
  • Combine RUN: RUN apt-get update && apt-get install -y X && rm -rf /var/lib/apt/lists/* trong 1 layer — clean apt cache cùng layer
  • .dockerignore bỏ node_modules, .git, test files khỏi build context
  • npm install --omit=dev hoặc --production

Performance

  • Layer cache order — package.json trước code
  • BuildKit (mặc định Docker 23+): build song song, cache mount
  • Cache mount: RUN --mount=type=cache,target=/root/.npm npm install — npm cache persist giữa các build
ℹ️ Compare image size
  • node:20 (Debian-based): ~1.1 GB
  • node:20-slim (Debian slim): ~250 MB
  • node:20-alpine: ~150 MB
  • gcr.io/distroless/nodejs20: ~140 MB
Demo / production thường dùng alpine. Lưu ý alpine dùng musl libc thay glibc — đôi khi gặp issue với native binary (canvas, sharp...).

# Stage 2 hoan toan moi -- KHONG ke thua tu builder

# curl de healthcheck, dumb-init de handle signals dung cach

# --no-cache de khong save apk cache -> image gon hon

# -S = system user (no password, no shell)

RUN npm install --omit=dev && npm cache clean --force
# Chi prod deps (khong typescript, jest...)
# Clean cache cung layer -> image nho hon

# Copy built output tu stage builder
COPY --from=builder --chown=nodejs:nodejs /app/dist ./dist
#      ^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^
#      lay tu stage    set owner luc copy (1 layer, hieu qua)

USER nodejs
# Tu day tro di chay nhu user nodejs (uid 1001)
EXPOSE 5000
# Document port -- khong tu publish, can -p khi run

# Docker tu check container alive moi 30s
HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD curl -f http://localhost:5000/api/health || exit 1
# --start-period: cho app 40s khoi dong xong moi tinh la fail
# --retries=3: 3 lan fail lien tiep moi unhealthy

ENTRYPOINT ["dumb-init", "--"]
# dumb-init: PID 1 dung tinh, forward signal SIGTERM toi node
# Khong co dumb-init: node thanh PID 1 -> signal handling weird,
# zombie process khong reap, docker stop cham vi SIGTERM bi an

CMD ["node", "dist/index.js"]
# Chay app -- truyen vao dumb-init lam arg
🎯 Tại sao Dockerfile này tốt
  • Multi-stage → image final ~150MB thay vì 1.5GB
  • Layer cache đúng thứ tự (package.json trước code)
  • Non-root user (security)
  • dumb-init handle signal đúng → docker stop graceful trong 5s
  • HEALTHCHECK built-in → docker biết container có "alive" thật không, không chỉ "running"
  • --no-cache + npm cache clean → image gọn

e. Mổ xẻ docker-compose.yml của project

Lấy docker-compose.yml của project, phân tích từng phần:

services:

  # ─── PostgreSQL ─────────────────────────────────────
  db:
    image: postgres:15-alpine                # Image official, alpine nho
    container_name: myapp-db                 # Ten cu the (de SSH vao dockge bao tri)
    restart: unless-stopped                  # Auto restart neu crash, tru khi user stop tay
    environment:
      POSTGRES_DB:       ${DB_NAME}          # Substitution tu host env / .env file
      POSTGRES_USER:     ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      # Persistent data -- DB con khi xoa container
      - postgres_data:/var/lib/postgresql/data
      # init.sql chay TU DONG lan dau khi volume RONG
      - ./backend/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
    ports:
      - "5433:5432"                       # Expose port -> dung pgAdmin/DBeaver tu host
                                              # 5433 host vi 5432 hay conflict voi local PG
    networks: [app-net]
    healthcheck:
      # pg_isready: lenh ping cua postgres
      # PG container co lenh nay san
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s       # Check moi 10s
      timeout: 5s         # Toi da 5s phai phan hoi
      retries: 5          # 5 lan fail moi tinh unhealthy

  # ─── Backend ─────────────────────────────────────────
  backend:
    build:
      context: ./backend          # Build context = thu muc ./backend
      dockerfile: Dockerfile      # Dockerfile trong context
    container_name: myapp-backend
    restart: unless-stopped
    env_file: ./backend/.env      # Load ca file .env vao env
    environment:
      DB_HOST: db                 # Resolve nho Docker DNS -> container db
      DB_PORT: 5432
      NODE_ENV: development
    ports:
      - "5000:5000"             # Expose API ra host:5000 de test
    depends_on:
      db:
        condition: service_healthy   # Doi DB pass healthcheck moi start backend
                                       # KHONG chi cho container running -- ma cho HEALTHY
    networks: [app-net]
    volumes:
      - ./backend/src:/app/src     # Hot-reload: thay code host -> thay code container
                                     # (chi co tac dung neu image co nodemon)

  # ─── Frontend ────────────────────────────────────────
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: myapp-frontend
    restart: unless-stopped
    depends_on: [backend]      # Start sau backend (nhung khong wait healthy)
    networks: [app-net]
    # KHONG expose port -- chi nginx (proxy) thay no

  # ─── Nginx reverse proxy ────────────────────────────
  nginx:
    image: nginx:1.25-alpine
    container_name: myapp-nginx
    restart: unless-stopped
    ports:
      - "80:80"                  # Cong giao tiep voi user
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [frontend, backend]
    networks: [app-net]

volumes:
  postgres_data:               # Volume name = "<project>_postgres_data"

networks:
  app-net:
    driver: bridge             # Network rieng, isolation tot
🎯 Pattern phổ biến trong compose này
  • 1 reverse proxy (nginx) — expose 1 port duy nhất ra host, route đến các backend
  • DB không expose ra public — chỉ map port khi cần (DBeaver/pgAdmin)
  • Healthcheck-based depends_on — backend không start cho đến khi DB ready
  • Service-name DNS — backend gọi db:5432 chứ không IP
  • Named volume cho DB — persistent across container recreation
  • Bind mount cho config — sửa nginx.conf không cần rebuild image

f. Override files — dev/staging/prod

Project này có 2 file:

  • docker-compose.yml — dev (build local, hot-reload, port expose)
  • docker-compose.prod.yml — prod (image từ ECR, không build, không bind src)

Cách 1 — chạy file rõ ràng:

docker compose -f docker-compose.prod.yml up -d

Cách 2 — override pattern (compose load 2 file, file sau merge đè file trước):

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
# Tat ca service tu file 1, ghi de boi file 2

Cách 3 — auto load docker-compose.override.yml nếu có:

docker compose up -d
# Tu load docker-compose.yml + docker-compose.override.yml (neu co)
ℹ️ Project hiện dùng cách 1 Local dev: docker compose up -d (load docker-compose.yml).
Production: docker compose -f docker-compose.prod.yml up -d trên EC2 (CI deploy).
Cách 1 rõ ràng hơn, dễ trace.

c. HEALTHCHECK — không nên thiếu

Healthcheck giúp Docker / Compose / Orchestrator biết container có "thực sự sống" không (process chạy không có nghĩa là app sẵn sàng nhận traffic).

2 cách khai báo

# Cach 1: Trong Dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD curl -f http://localhost:5000/api/health || exit 1

# Cach 2: Trong compose
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:5000/api/health"]
  interval: 30s
  timeout: 10s
  start_period: 40s
  retries: 3

Parameters

  • interval: bao lâu check 1 lần (default 30s)
  • timeout: lệnh check phải hoàn thành trong thời gian này (default 30s)
  • start_period: lúc đầu cho app thời gian boot, fail không tính (default 0s)
  • retries: bao nhiêu lần fail liên tiếp mới đánh dấu unhealthy (default 3)

Health states

StateNghĩa
startingTrong start_period, chưa tính
healthyCheck pass
unhealthyFail quá retries lần liên tiếp
docker ps
# STATUS: Up 5 minutes (healthy)

docker inspect --format '{{.State.Health.Status}}' myapp-backend
# Xem chi tiet healthcheck logs:
docker inspect --format '{{json .State.Health}}' myapp-backend | jq
🎯 Tại sao healthcheck quan trọng trong production
  • compose: depends_on: condition: service_healthy đợi service ready
  • Docker Swarm / ECS / K8s: dùng healthcheck để tự restart container unhealthy
  • ALB target group: ALB tự gửi request /health, phối hợp với container healthcheck
  • Không healthcheck → orchestrator chỉ biết container "running" nhưng có thể đang hang

d. Resource limits — CPU, RAM, file descriptors

Default container có thể dùng toàn bộ CPU + RAM của host. App leak → host chết.

# docker run
docker run -d \
  --cpus="0.5"           # 50% 1 CPU core \
  -m 512m                # 512 MB RAM (OOMKilled neu vuot) \
  --memory-swap=512m     # Khong cho dung swap \
  --pids-limit=200       # Toi da 200 process trong container \

g. Init system — vì sao cần dumb-init / tini

PID 1 problem

Trong container, process đầu tiên là PID 1 — special. Linux kernel:

  • PID 1 phải reap (cleanup) zombie process
  • PID 1 nhận signal đặc biệt — SIGTERM gửi vào PID 1 không có default handler → bị ignore

Node.js / Python / Ruby... thường KHÔNG handle PID 1 việc reap. Hậu quả:

  • docker stop gửi SIGTERM → app bỏ qua → đợi 10s timeout → SIGKILL → exit 137
  • Zombie process tích tụ → file descriptor leak

Giải pháp: init wrapper

# dumb-init (cu nhung phai bien)
RUN apk add --no-cache dumb-init
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "app.js"]

# Hoac tini (giong, cua Krallin)
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "app.js"]

# Hoac dung --init flag cua Docker (Docker tu add tini)
docker run --init myapp
ℹ️ Project này dùng dumb-init Xem backend/Dockerfile dòng 35: ENTRYPOINT ["dumb-init", "--"]. Khi docker stop, dumb-init forward SIGTERM tới Node.js → Node.js shutdown gracefully trong <5s thay vì 10s + kill.

h. User non-root

Default container chạy as root (uid 0). Nếu RCE → attacker có root trong container → đôi khi escape ra host.

# Tao user nodejs uid 1001 trong Dockerfile
RUN addgroup -g 1001 nodejs && adduser -S -u 1001 -G nodejs nodejs
#         ^^^^^^^^                    ^^^^^^^^
#         system group                 system user (-S = no password, no shell)

# COPY voi --chown=nodejs:nodejs
COPY --from=builder --chown=nodejs:nodejs /app/dist ./dist

# Switch user TRUOC khi CMD
USER nodejs

# Tu day moi instruction chay nhu user nodejs
CMD ["node", "dist/index.js"]
⚠️ Bind volume + non-root Khi mount host folder vào container non-root, owner trên host phải match (vd chown -R 1001:1001 ./data). Nếu không, container không write được.
