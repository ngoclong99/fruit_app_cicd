2. Module A — CloudFront serve Frontend (S3)

📖 Doc chi tiết Module này đã có doc riêng: S3_FRONTEND.md (7 phase + cutover). Phần dưới đây là tóm tắt + bổ sung UI walkthrough.

Tại sao migrate

Hiện tại frontend serve qua nginx trên EC2 → EC2 down ban đêm thì FE cũng down. Migrate sang S3 static hosting + CloudFront:

  • FE accessible 24/7 (S3 99.99% SLA)
  • Tốc độ nhanh hơn (CDN edge gần user)
  • Cost gần $0 (free tier 1TB/tháng vĩnh viễn)
  • EC2 chỉ cần phục vụ api.vhnlong.store → có thể downgrade t3.small → t3.micro

Kiến trúc đích

vhnlong.store ─► CloudFront (alias) ─► S3 bucket (private) "vhnlong-frontend" /index.html /assets/... /static/... api.vhnlong.store ─► ALB (alias) ─► EC2 / ECS backend

Các bước chính

  1. Tạo S3 bucket cho frontend (similar S3_IMAGES nhưng dùng cho static site)
  2. Build & upload: cd frontend && npm run build && aws s3 sync dist/ s3://vhnlong-frontend/
  3. CloudFront distribution:
    • Origin: S3 bucket qua OAC (như đã làm cho images)
    • Default root object: index.html
    • Custom error pages: 403/404 → /index.html 200 (SPA routing)
    • Behavior: /* cache long, /index.html no-cache
  4. ACM cert ở us-east-1 (CloudFront ONLY accept us-east-1 cert — KHÁC ALB)
  5. Route 53: vhnlong.store → CloudFront alias
  6. Tách backend domain: tạo api.vhnlong.store → ALB
  7. Sửa frontend env: VITE_API_URL=https://api.vhnlong.store
  8. Update CI: split deploy thành 2 workflow (frontend → S3+invalidate, backend → ECS/ASG)

S3 bucket policy cho CloudFront OAC

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::vhnlong-frontend/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::529568113348:distribution/<DIST_ID>"
      }
    }
  }]
}

Custom error pages cho SPA routing

SPA dùng client-side routing (React Router). User vào /admin/products trực tiếp → S3 trả 403/404 vì không có file đó. Cần CloudFront error response:

Như vậy mọi URL không match file → trả index.html → React Router tự xử lý.

CI deploy frontend script

# .github/workflows/deploy-frontend.yml
- name: Build frontend
  run: |
    cd frontend
    npm install

- name: Sync to S3
  run: |

      --delete \

      --exclude index.html

- name: Invalidate CloudFront
  run: |
    aws cloudfront create-invalidation \
      --distribution-id $CF_DIST_ID \
      --paths "/index.html" "/"

3. Module B — WAF (Web Application Firewall)

WAF làm gì

Đứng trước ALB hoặc CloudFront, inspect mỗi HTTP request và block / allow / count theo rule:

  • Rate limit: 1 IP > 2000 req/5 phút → block
  • Geo block: chặn IP từ countries cụ thể
  • SQL injection / XSS detection (managed rule)
  • Bot control (managed rule, có phí riêng)
  • Custom rules: chặn theo header, URI, body...

B1 Quyết định attach vào ALB hay CloudFront

Attach vàoRegion WAF phải tạoScope
ALBCùng region ALB (ap-southeast-1)Regional WebACL
CloudFrontus-east-1 (BẮT BUỘC)Global / CLOUDFRONT scope
💡 Best Attach vào CloudFront (filter trước khi vào origin) + giữ ALB tách biệt. Demo này có thể bắt đầu với ALB nếu chưa có CloudFront cho backend.

B2 Tạo WAF Web ACL (UI)

AWS Console UI
  1. Console → WAF & Shield → Web ACLs → Create web ACL
  2. Resource type:
    • Regional resources (ALB, API Gateway...) → region ap-southeast-1
    • HOẶC CloudFront distributions → region tự động us-east-1
  3. Name: myapp-waf
  4. CloudWatch metric name: myapp-waf
  5. Add AWS resources: chọn myapp-alb (hoặc CloudFront distribution)
  6. Next → Add rules and rule groups

B3 Add Managed Rule Groups (free + recommended)

  1. AWS Managed Rules: AWSManagedRulesCommonRuleSet (chặn OWASP top 10 cơ bản)
  2. AWSManagedRulesKnownBadInputsRuleSet (chặn known malicious patterns)
  3. AWSManagedRulesAmazonIpReputationList (chặn IP có lịch sử xấu)
  4. AWSManagedRulesSQLiRuleSet (SQL injection)

Mỗi managed rule: chọn Count trước (chỉ log, không block) trong vài ngày để xem có false positive không, rồi đổi sang Block.

B4 Add custom rate limit rule

  1. Add my own rules → Rule builder
  2. Name: rate-limit-per-ip
  3. Type: Rate-based rule
  4. Rate limit: 2000 requests per 5 minute period per IP
  5. Action: Block
  6. Add rule

B5 Default action + priority

  • Default action (request không match rule nào): Allow
  • Priority: rate-limit ưu tiên cao (chạy trước), managed rules sau

C2 App đọc secret

Cách 1 — ECS Fargate (đẹp nhất):

# Task definition - format valueFrom cho Secrets Manager:
#   arn:aws:secretsmanager:<region>:<account>:secret:<name>-<random>:<json-key>:<version-stage>:<version-id>
#                                                                       ^                ^                ^
#                                                                       |                |                |
#                                          ten field trong JSON (vd "username")    AWSCURRENT (mac dinh)  rong (mac dinh)
#
# Cu phap full: ":username:AWSCURRENT:"
# Rut gon (de empty cho default): ":username::"  -- 2 dau ":" cuoi BAT BUOC co
"secrets": [
  { "name": "DB_USERNAME", "valueFrom": "arn:aws:secretsmanager:ap-southeast-1:529568113348:secret:myapp/production/db-credentials-AbCdEf:username::" },
  { "name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:ap-southeast-1:529568113348:secret:myapp/production/db-credentials-AbCdEf:password::" }
]
ℹ️ Secret ARN có random suffix Mỗi Secrets Manager secret có hậu tố 6 ký tự random (vd -AbCdEf) — AWS thêm để chống "secret hijacking" (kẻ xấu xóa secret rồi tạo lại cùng tên). Lấy ARN đầy đủ bằng: aws secretsmanager describe-secret --secret-id myapp/production/db-credentials --query ARN --output text

Cách 2 — Node.js đọc lúc startup:

import { SecretsManagerClient, GetSecretValueCommand } from '@aws-sdk/client-secrets-manager';

async function getSecret(name: string) {
  const client = new SecretsManagerClient({ region: 'ap-southeast-1' });
  const { SecretString } = await client.send(new GetSecretValueCommand({ SecretId: name }));
  return JSON.parse(SecretString!);
}

const dbCreds = await getSecret('myapp/production/db-credentials');
// dbCreds.username, dbCreds.password

RDS auto rotation flow

1. Secrets Manager Lambda chay theo schedule (30 ngay) 2. Lambda tao password moi 3. Lambda goi RDS ModifyDBInstance MasterUserPassword 4. RDS update password (online, khong downtime) 5. Lambda update Secret voi password moi 6. App o reboot ke tiep doc password moi (hoac dung "AWSCURRENT" -- secret auto cap nhat)

5. Module C2 — KMS (Key Management Service)

KMS là gì

Encryption key management: tạo/lưu trữ/quản lý keys, AWS sẽ encrypt/decrypt data thay bạn. Bạn không bao giờ thấy key thô (lưu trong HSM).

3 loại key

LoạiCostUse case
AWS-owned keysFREEDefault cho 1 số service (vd S3 SSE-S3). AWS quản hoàn toàn, không thấy
AWS-managed keys (vd aws/s3, aws/rds)FREE1 key/service/region. AWS rotate annual
Customer-managed keys (CMK)$1/key/tháng + $0.03/10k requestsKhi cần audit access ai dùng key, cross-account share, manual rotation

Tạo CMK

# 1. Tao key
$keyArn = aws kms create-key --region ap-southeast-1 `
  --description "myapp encryption key" `
  --key-usage ENCRYPT_DECRYPT `
  --query "KeyMetadata.Arn" --output text

# 2. Tao alias (friendly name)
aws kms create-alias --alias-name alias/myapp-key --target-key-id $keyArn

# 3. Bat key rotation (tu dong moi nam)
aws kms enable-key-rotation --key-id $keyArn

# 4. Encrypt data tu CLI
$plaintext = "super-secret-password"
$ciphertext = aws kms encrypt --key-id alias/myapp-key `
  --plaintext (-join ([byte[]][char[]]$plaintext | ForEach-Object { $_.ToString("X2") })) `
  --query "CiphertextBlob" --output text

# 5. Decrypt
aws kms decrypt --ciphertext-blob fileb://<...> --query "Plaintext" --output text

Use KMS với S3

# Upload object voi SSE-KMS
aws s3 cp file.txt s3://my-bucket/file.txt `
  --sse aws:kms --sse-kms-key-id alias/myapp-key

# Default encryption cho ca bucket
aws s3api put-bucket-encryption --bucket my-bucket --server-side-encryption-configuration '{
  "Rules": [{
    "ApplyServerSideEncryptionByDefault": {
      "SSEAlgorithm": "aws:kms",
      "KMSMasterKeyID": "alias/myapp-key"
    }
  }]
}'

Use KMS với RDS / EBS

# RDS: chi luc tao instance moi co option storage-encrypted + kms-key-id
aws rds create-db-instance ... --storage-encrypted --kms-key-id alias/myapp-key

# EBS: tao volume voi encryption
aws ec2 create-volume --size 10 --availability-zone ap-southeast-1a `
  --encrypted --kms-key-id alias/myapp-key

Envelope encryption — pattern khi encrypt data lớn

KMS encrypt được tối đa 4KB. Cho data lớn (file, DB column):

  1. App gọi kms.GenerateDataKey → trả về plaintext data key + encrypted data key
  2. App dùng plaintext data key encrypt data (local, AES-256)
  3. App lưu: encrypted data + encrypted data key
  4. Khi decrypt: app gọi kms.Decrypt data key → decrypt data với plaintext key

6. Module C3 — Cognito (Managed User Auth)

Cognito là gì

Quản lý user signup/signin + JWT generation. Thay vì viết auth từ đầu (như project hiện tại với JWT_SECRET), Cognito lo:

  • Signup / signin flows + email verification
  • JWT token generation + validation
  • MFA (SMS, TOTP)
  • Social login (Google, Facebook, Apple)
  • Password policy + reset
  • User pool quản lý hàng triệu user

Architecture

User browser │ │ 1. POST /signup {email, password} ▼ Frontend ──► Cognito User Pool ──► Email verification │ │ │ │ 2. POST /signin │ ▼ │ Issue JWT (id_token + access_token) │ │ │ 3. Send token in Authorization header ▼ Backend / API Gateway │ │ 4. Verify JWT signature with Cognito public keys (JWKS) │ (Free, no Cognito API call needed) │ ▼ Process request

Tạo User Pool

# Tao user pool
$pool = aws cognito-idp create-user-pool --region ap-southeast-1 `
  --pool-name myapp-users `
  --policies "PasswordPolicy={MinimumLength=8,RequireUppercase=true,RequireNumbers=true}" `
  --auto-verified-attributes email `
  --username-attributes email `
  --query "UserPool.{Id:Id,Arn:Arn}" --output json | ConvertFrom-Json

# Tao app client (cho frontend dung)
aws cognito-idp create-user-pool-client --user-pool-id $pool.Id `
  --client-name myapp-web `
  --no-generate-secret # SPA khong dung client secret `
  --explicit-auth-flows ALLOW_USER_SRP_AUTH ALLOW_REFRESH_TOKEN_AUTH

Frontend sign up + sign in (AWS Amplify Auth)

import { Amplify } from "aws-amplify";
import { signUp, signIn, signOut, getCurrentUser } from "aws-amplify/auth";

  Auth: { Cognito: {

  username: "user@example.com",

// Trong middleware

  const payload = await verifier.verify(jwtFromHeader);

}

7. Module C4 — VPC deep (private subnets + NAT + endpoints)

Tại sao VPC deep

Mặc định default VPC có 3 subnet PUBLIC — EC2 lấy public IP, accessible từ internet. Production thực sự: backend nên ở private subnet, chỉ ALB ở public.

┌─────────── VPC ───────────────────────────────────────────┐ │ │ │ PUBLIC SUBNET (ap-southeast-1a) │ │ ┌──────────────────────────────┐ │ │ │ ALB (public IP) │ ◄── User from internet │ │ │ NAT Gateway (public IP) │ │ │ └──────────────────────────────┘ │ │ │ │ │ ▼ Forward to private subnet │ │ │ │ PRIVATE SUBNET (ap-southeast-1a) │ │ ┌──────────────────────────────┐ │ │ │ EC2 / ECS (NO public IP) │ │ │ │ RDS (NO public IP) │ │ │ │ ElastiCache │ │ │ └────────┬─────────────────────┘ │ │ │ Outbound internet (npm install, AWS API) │ │ ▼ via NAT Gateway (public) │ │ │ │ PRIVATE SUBNET (ap-southeast-1b) -- duplicate for HA │ │ │ └───────────────────────────────────────────────────────────┘ │ ▼ Internet Gateway (IGW)

4 thành phần VPC quan trọng

ComponentMục đíchCost
VPCNetwork isolation, CIDR riêng (vd 10.0.0.0/16)FREE
Subnet (public)Có route đến IGW. Resource trong này có thể public IPFREE
Subnet (private)Không có route IGW. Outbound qua NATFREE
Internet Gateway (IGW)Route VPC ↔ internetFREE
NAT GatewayPrivate subnet outbound internet (1 chiều)$0.045/h + $0.045/GB processed = ~$32/tháng/AZ
VPC Endpoint (Gateway)Private access đến S3/DynamoDB không qua internetFREE
VPC Endpoint (Interface)Private access đến ECR/Secrets Manager/etc~$7.30/mỗi endpoint/tháng + $0.01/GB
⚠️ NAT Gateway DỄ TỐN TIỀN Production HA cần 1 NAT/AZ → 3 NAT = ~$96/tháng. Cho demo, dùng 1 NAT chung hoặc NAT Instance (EC2 + SourceDestCheck=false, rẻ hơn).

Setup architecture đề xuất cho project

  1. VPC mới 10.0.0.0/16
  2. 2 subnet public 10.0.1.0/24 + 10.0.2.0/24 — cho ALB
  3. 2 subnet private 10.0.11.0/24 + 10.0.12.0/24 — cho EC2/ECS + RDS
  4. 1 IGW attach vào VPC
  5. 1 NAT Gateway trong subnet public (cho demo — không HA NAT)
  6. Route table public: 0.0.0.0/0 → IGW
  7. Route table private: 0.0.0.0/0 → NAT
  8. VPC Endpoint Gateway cho S3 + DynamoDB (FREE — tiết kiệm NAT cost)

Migrate project hiện tại sang VPC private

Hiện EC2 ở default VPC public subnet. Để migrate:

  1. Tạo VPC + subnets như trên
  2. Move/recreate EC2 vào private subnet (instance không có public IP)
  3. SSH vào EC2: phải qua bastion host (EC2 ở public subnet) hoặc dùng SSM Session Manager (không cần SSH port, không cần bastion)
  4. ALB ở public subnet → forward đến EC2 ở private
  5. EC2 outbound (pull ECR, gọi SSM): qua NAT Gateway hoặc qua VPC Endpoints

SSM Session Manager — replace SSH

# Cho phep SSM agent tren EC2 (mac dinh co o Amazon Linux 2)
# Ubuntu can cai:

# IAM role EC2 can policy AmazonSSMManagedInstanceCore

6.1 S3 Cross-Region Replication (CRR)

Replicate object từ ap-southeast-1 sang ap-southeast-2 tự động:

# 1. Tao bucket o region dich
aws s3api create-bucket --bucket vhnlong-images-dr --region ap-southeast-2 `
  --create-bucket-configuration LocationConstraint=ap-southeast-2

# 2. Versioning bat buoc cho CRR
aws s3api put-bucket-versioning --bucket vhnlong-images --versioning-configuration Status=Enabled
aws s3api put-bucket-versioning --bucket vhnlong-images-dr --versioning-configuration Status=Enabled

# 3. Tao IAM role cho replication
# 4. Apply replication config (JSON)
aws s3api put-bucket-replication --bucket vhnlong-images --replication-configuration file://replication.json

6.2 RDS cross-region read replica

aws rds create-db-instance-read-replica `
  --db-instance-identifier myapp-prod-db-dr `
  --source-db-instance-identifier arn:aws:rds:ap-southeast-1:529568113348:db:myapp-prod-db `
  --region ap-southeast-2

Khi region chính chết → promote replica thành primary:

aws rds promote-read-replica --db-instance-identifier myapp-prod-db-dr --region ap-southeast-2

6.3 Route 53 failover routing

Có 2 record cùng vhnlong.store:

  • Record PRIMARY: ALIAS → ALB ap-southeast-1, healthcheck đính kèm
  • Record SECONDARY: ALIAS → ALB ap-southeast-2, không healthcheck

Khi ALB primary fail healthcheck → Route 53 tự trả về SECONDARY.
