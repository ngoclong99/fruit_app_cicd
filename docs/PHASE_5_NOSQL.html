1. Tại sao cần NoSQL + async messaging

Phase 1-4 đã đủ build 1 web app monolith. Để scale lên + handle traffic biến động, cần 2 paradigm:

PatternVấn đề giải quyếtService AWS
NoSQLRDS schema rigid, scale ngang khó. NoSQL key-value scale unlimited, latency mili-secondDynamoDB, DocumentDB
QueueSync API blocking — user phải đợi. Queue cho phép producer publish + consumer xử lý sauSQS, Kinesis
Pub/Sub1 event → nhiều subscriber (gửi email + log + analytics)SNS, EventBridge
CacheQuery DB chậm, lặp lại → cache lưu RAM, milli-second responseElastiCache (Redis), DAX cho DynamoDB

2. NoSQL vs SQL — khi nào dùng cái nào

Tiêu chíRDS (PostgreSQL/MySQL)DynamoDB
SchemaStrict — cần migration mỗi lần đổi columnFlexible — mỗi row có field khác nhau OK
Query phức tạp (JOIN, GROUP BY)✅ Mạnh❌ Không có JOIN. Phải denormalize
Transaction (ACID)✅ Full ACID multi-row⚠️ Transaction giới hạn (max 100 item, 1 region)
ScaleVertical scale (instance lớn hơn). Horizontal scale phức tạp (sharding)✅ Horizontal native — partition tự động, unlimited scale
Latency1-10ms (small queries)<10ms guaranteed at any scale
Cost modelPer instance/hour (luôn chạy)Per request + storage (on-demand) hoặc provisioned RCU/WCU
Best forApp có quan hệ phức tạp, reporting, OLAPKey-value lookup, session store, IoT, gaming leaderboard, high-throughput
💡 Heuristic chọn nhanh Nếu query của bạn luôn dùng "WHERE id = X" hoặc "WHERE user_id = X" — DynamoDB tốt hơn (single-digit ms, scale unlimited). Nếu cần JOIN nhiều table hoặc query "WHERE created_at BETWEEN ... AND status = ..." — RDS tốt hơn.

3. Part 1 — DynamoDB

a. Khái niệm: partition key, sort key, GSI, LSI

┌─────────────────────────────────────────────────────────┐ │ TABLE: orders │ │ │ │ Partition Key (PK) -- BAT BUOC. Hash de phan partition │ │ orderId (vd "ORD-001", "ORD-002") │ │ │ │ Sort Key (SK) -- OPTIONAL. Sort trong cung partition │ │ createdAt (vd "2026-05-25T10:00:00Z") │ │ │ │ Attributes -- KHONG can declare truoc (schemaless) │ │ userId, total, items, status, ... │ │ │ │ ↓ │ │ │ │ Primary Key = PK + SK (composite) │ │ - Voi 1 orderId, co the co nhieu SK khac nhau │ │ - Vd 1 user co nhieu order qua thoi gian │ └─────────────────────────────────────────────────────────┘

Partition: cách DynamoDB scale

DynamoDB chia data thành nhiều partition (mỗi cái 10GB + 1000 WCU + 3000 RCU). Hash của Partition Key quyết định item đi vào partition nào.

⚠️ Hot partition problem Nếu chọn PK kém (vd partitionKey = "DAY" với cùng giá trị cho mọi row), tất cả request đổ vào 1 partition → throttle. Phải chọn PK high-cardinality (nhiều giá trị unique).

GSI (Global Secondary Index) vs LSI (Local Secondary Index)

—GSILSI
Khi tạoBất kỳ lúc nào (sau khi table tạo)Chỉ lúc tạo table
Partition KeyKhác PK của tableCùng PK với table
Sort KeyCó thể khácKhác SK của table
CapacityRiêng (RCU/WCU độc lập)Share với table
ConsistencyEventually consistentStrongly consistent option có
Use caseQuery theo attribute khác (vd query order by status)Query cùng PK nhưng sort theo field khác

b. Tạo table

aws dynamodb create-table --region ap-southeast-1 `
  --table-name myapp-orders `
  --attribute-definitions `
    AttributeName=orderId,AttributeType=S `
    AttributeName=createdAt,AttributeType=S `
    AttributeName=userId,AttributeType=S `
  --key-schema `
    AttributeName=orderId,KeyType=HASH `
    AttributeName=createdAt,KeyType=RANGE `
  --global-secondary-indexes `
    "[{
      \"IndexName\": \"by-user\",
      \"KeySchema\": [
        {\"AttributeName\": \"userId\", \"KeyType\": \"HASH\"},
        {\"AttributeName\": \"createdAt\", \"KeyType\": \"RANGE\"}
      ],
      \"Projection\": {\"ProjectionType\": \"ALL\"}
    }]" `
  --billing-mode PAY_PER_REQUEST

Giải thích:

  • HASH = partition key, RANGE = sort key
  • PAY_PER_REQUEST = on-demand billing — không cần dự đoán capacity, AWS tính per request. Phù hợp demo + traffic biến động
  • Alternative: PROVISIONED với RCU/WCU cố định — rẻ hơn nếu traffic ổn định
  • GSI by-user cho phép query "tất cả order của 1 user" — table primary chỉ query được "order theo orderId"

c. CRUD operations

PutItem (insert hoặc replace)

aws dynamodb put-item --region ap-southeast-1 `
  --table-name myapp-orders `
  --item '{
    "orderId": {"S": "ORD-001"},
    "createdAt": {"S": "2026-05-25T10:00:00Z"},
    "userId": {"S": "USR-100"},
    "total": {"N": "445000"},
    "status": {"S": "pending"},
    "items": {"L": [
      {"M": {"productId": {"S": "PROD-1"}, "qty": {"N": "2"}}
    ]}
  }'

Lưu ý format AttributeValue: S=String, N=Number (string trong JSON), B=Binary, BOOL=Boolean, L=List, M=Map, SS/NS=String/Number Set, NULL.

GetItem (lookup by primary key)

aws dynamodb get-item --region ap-southeast-1 `
  --table-name myapp-orders `
  --key '{
    "orderId": {"S": "ORD-001"},
    "createdAt": {"S": "2026-05-25T10:00:00Z"}
  }'

UpdateItem (partial update)

aws dynamodb update-item --region ap-southeast-1 `
  --table-name myapp-orders `
  --key '{"orderId": {"S": "ORD-001"}, "createdAt": {"S": "2026-05-25T10:00:00Z"}}' `
  --update-expression "SET #s = :newStatus" `
  --expression-attribute-names '{"#s": "status"}' `
  --expression-attribute-values '{":newStatus": {"S": "shipped"}}'

Lưu ý: status là reserved word của DynamoDB → phải dùng placeholder #s. Tương tự với value :newStatus để tránh injection.

DeleteItem

aws dynamodb delete-item --region ap-southeast-1 `
  --table-name myapp-orders `
  --key '{"orderId": {"S": "ORD-001"}, "createdAt": {"S": "2026-05-25T10:00:00Z"}}'

d. Query vs Scan — KHÁC BIỆT lớn

—QueryScan
Cách hoạt độngTìm theo PK (+ optional SK condition). Chỉ đọc 1 partitionĐọc toàn bộ table, filter theo condition
Cost (RCU)Rất thấp — chỉ tính item matchRất cao — tính mọi item trong table
Tốc độMili-secondGiây-phút tùy size
Khi nào dùng99% queriesLast resort — admin task, hoặc ETL

Query example — tất cả order của user qua GSI

aws dynamodb query --region ap-southeast-1 `
  --table-name myapp-orders `
  --index-name by-user `
  --key-condition-expression "userId = :uid" `
  --expression-attribute-values '{":uid": {"S": "USR-100"}}' `
  --scan-index-forward false # sort descending by createdAt

Scan example — count toàn bộ order pending

# DUNG it -- co the ton RCU lon
aws dynamodb scan --region ap-southeast-1 `
  --table-name myapp-orders `
  --filter-expression "#s = :pending" `
  --expression-attribute-names '{"#s": "status"}' `
  --expression-attribute-values '{":pending": {"S": "pending"}}' `
  --select COUNT

Node.js example (AWS SDK v3)

import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, QueryCommand, PutCommand } from "@aws-sdk/lib-dynamodb";

// DocumentClient marshall/unmarshall JS object <-> DynamoDB format tu dong
const client = new DynamoDBClient({ region: "ap-southeast-1" });
const ddb = DynamoDBDocumentClient.from(client);

// Put -- khong can {S: ...}, {N: ...} nua
await ddb.send(new PutCommand({
  TableName: "myapp-orders",
  Item: { orderId: "ORD-001", createdAt: "2026-05-25T10:00:00Z", total: 445000 }
}));

// Query GSI
const result = await ddb.send(new QueryCommand({
  TableName: "myapp-orders",
  IndexName: "by-user",
  KeyConditionExpression: "userId = :uid",
  ExpressionAttributeValues: { ":uid": "USR-100" }
}));
console.log(result.Items);

e. DynamoDB Streams — trigger Lambda khi data đổi

Streams ghi lại mọi INSERT/UPDATE/DELETE trên table thành event stream. Lambda có thể consume → tạo workflow event-driven.

# 1. Bat stream khi tao table
aws dynamodb update-table --table-name myapp-orders `
  --stream-specification "StreamEnabled=true,StreamViewType=NEW_AND_OLD_IMAGES"

# 2. Tao Lambda
# 3. Map Lambda voi stream
$streamArn = aws dynamodb describe-table --table-name myapp-orders `
  --query "Table.LatestStreamArn" --output text

aws lambda create-event-source-mapping `
  --function-name myapp-order-processor `
  --event-source-arn $streamArn `
  --starting-position LATEST `
  --batch-size 10

Use case Streams

  • Real-time analytics: order tạo → update aggregations
  • Email notification khi order ship
  • Audit log: copy mọi change vào CloudWatch/S3
  • Cross-region replication custom
  • Search indexing: sync DynamoDB → OpenSearch

4. Part 2 — SQS (Simple Queue Service)

SQS là gì

Queue FIFO/Standard để decouple producer (đẩy message) và consumer (xử lý). Message tồn tại trong queue tối đa 14 ngày, hoặc tới khi consumer xóa (acknowledge).

PRODUCER SQS QUEUE CONSUMER (worker) [API receive ┌─────────────────┐ order request] │ msg-1: ORD-100 │ ┌──────────┐ │ │ msg-2: ORD-101 │ ──────► │ Lambda / │ └──── SendMessage │ msg-3: ORD-102 │ │ EC2 / │ │ ... │ ◄────── │ Fargate │ └─────────────────┘ DeleteMsg └──────────┘ Producer reply 200 Queue store msg Consumer pull, ngay -- khong cho trong toi 14 ngay process, delete worker xu ly xong

2 loại queue

StandardFIFO
At-least-once delivery (có thể duplicate)Exactly-once
Best-effort ordering (không guarantee)Strict ordering
Unlimited throughput300 msg/s default, 3000 với batching
Cost rẻ hơnCost cao hơn ~2×
Use: notification, logging, batch processingUse: order processing, financial transaction

Pattern điển hình: API → SQS → Lambda worker

# 1. Tao queue
$queueUrl = aws sqs create-queue --queue-name myapp-orders --region ap-southeast-1 `
  --query "QueueUrl" --output text

# 2. Send message
aws sqs send-message --queue-url $queueUrl `
  --message-body '{"orderId": "ORD-100", "action": "process"}'

# 3. Receive (Lambda tu dong receive khi mapping)
aws sqs receive-message --queue-url $queueUrl `
  --max-number-of-messages 10 --wait-time-seconds 20 # long polling

# 4. Delete sau khi xu ly thanh cong
aws sqs delete-message --queue-url $queueUrl --receipt-handle <handle>

Connect Lambda với SQS

aws lambda create-event-source-mapping `
  --function-name myapp-worker `
  --event-source-arn arn:aws:sqs:ap-southeast-1:529568113348:myapp-orders `
  --batch-size 10 `
  --maximum-batching-window-in-seconds 5

Lambda nhận event chứa mảng messages. Process từng message, throw error nếu fail → message quay lại queue retry.

Dead Letter Queue (DLQ)

Sau N retries, message fail nên đi vào queue khác (DLQ) để inspect thay vì lặp infinite:

aws sqs create-queue --queue-name myapp-orders-dlq

# Set redrive policy: sau 3 lan retry -> DLQ
aws sqs set-queue-attributes --queue-url $queueUrl --attributes `
  '{"RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:ap-southeast-1:529568113348:myapp-orders-dlq\",\"maxReceiveCount\":\"3\"}"}'

5. Part 3 — SNS (Simple Notification Service)

SNS = pub/sub. 1 publisher → nhiều subscriber. Khác với SQS (1 producer → 1 consumer queue).

┌─► Email subscriber ├─► SMS subscriber PUBLISHER ─► SNS TOPIC ──────►├─► Lambda function ├─► SQS queue └─► HTTPS endpoint (webhook)

Setup pattern

# 1. Tao topic
$topicArn = aws sns create-topic --name myapp-events `
  --query "TopicArn" --output text

# 2. Subscribe multiple endpoints
aws sns subscribe --topic-arn $topicArn --protocol email --notification-endpoint admin@example.com
aws sns subscribe --topic-arn $topicArn --protocol sqs --notification-endpoint <sqs-arn>
aws sns subscribe --topic-arn $topicArn --protocol lambda --notification-endpoint <lambda-arn>

# 3. Publish
aws sns publish --topic-arn $topicArn `
  --subject "Order placed" `
  --message "Order ORD-100 needs processing"

SNS vs SQS — khi nào dùng cái nào

SNS (pub/sub)SQS (queue)
Fanout — 1 event tới N subscribersWorkload distribution — 1 message → 1 consumer
Push model — SNS push to subscriberPull model — consumer poll queue
Real-time — message gửi ngay khi publishBuffered — message chờ trong queue
Không retry built-in (trừ HTTP endpoints)Retry tự động + DLQ pattern

SNS + SQS fanout pattern (rất phổ biến)

┌─► SQS-Email queue ─► Lambda send email PUBLISHER ─► SNS TOPIC ─────────┼─► SQS-Analytics queue ─► Lambda log to BigQuery └─► SQS-Search queue ─► Lambda update Algolia

Mỗi consumer có queue riêng → có thể retry/process at own pace mà không ảnh hưởng consumer khác.

6. Part 4 — EventBridge custom events

Phase 4 đã dùng EventBridge cho schedule (cron). Phase này: EventBridge custom event bus — pattern matching engine cho application events.

Default vs custom event bus

  • Default bus: nhận event AWS service (EC2 state change, S3 upload, CodeDeploy...)
  • Custom bus: app của bạn publish event vào → service khác subscribe

Publish custom event

# 1. Tao bus rieng cho app
aws events create-event-bus --name myapp-bus

# 2. Publish event tu code app
aws events put-events --entries '[{
  "Source": "myapp.orders",
  "DetailType": "OrderPlaced",
  "Detail": "{\"orderId\":\"ORD-100\",\"total\":445000}",
  "EventBusName": "myapp-bus"
}]'

# 3. Rule: bat moi event "OrderPlaced" tu source "myapp.orders"
aws events put-rule --name on-order-placed --event-bus-name myapp-bus `
  --event-pattern '{
    "source": ["myapp.orders"],
    "detail-type": ["OrderPlaced"]
  }'

# 4. Add target (Lambda / SQS / SNS / Step Functions / ...)
aws events put-targets --rule on-order-placed --event-bus-name myapp-bus `
  --targets "Id=1,Arn=arn:aws:lambda:ap-southeast-1:529568113348:function:notify-warehouse"

EventBridge vs SNS — khi nào dùng cái nào

EventBridgeSNS
Pattern matching mạnh — filter theo nhiều attributeSubscribe theo topic, không filter chi tiết
Schema registry — version eventsKhông có schema
Tích hợp 100+ AWS service + SaaS partner (Datadog, Auth0...)Chỉ AWS + email/SMS/HTTPS
Slower (~1s latency)Faster (~<100ms)
$1/1M event$0.50/1M publish

7. Part 5 — ElastiCache (Redis)

Managed Redis hoặc Memcached. Use case chính: caching layer trước DB.

Pattern: cache-aside

API → 1. GET cache:user:100 ─► Redis │ │ │ HIT? return ngay luon │ MISS │ ▼ │ PostgreSQL/DynamoDB │ │ ◄ 2. SET cache:user:100 ... TTL 5 phut
# Tao Redis cluster (single-node demo)
aws elasticache create-cache-cluster --region ap-southeast-1 `
  --cache-cluster-id myapp-redis `
  --engine redis `
  --cache-node-type cache.t4g.micro `
  --num-cache-nodes 1 `
  --security-group-ids <sg-allow-from-ec2>

Use case ElastiCache cho project

  • Session store: JWT token blacklist, user session data
  • Cache DB query: top products, popular searches
  • Rate limiting: count request per IP per minute
  • Leaderboard: Redis sorted set rất hiệu quả
  • Pub/sub trong-process: Redis Pub/Sub thay SNS cho real-time low-latency

Cost

Instance typeRAMCost ap-southeast-1
cache.t4g.micro0.5 GB~$11/tháng
cache.t4g.small1.4 GB~$22/tháng
cache.r7g.large13 GB~$130/tháng

8. 6 pattern event-driven phổ biến

Pattern 1: Order processing

User submit order ──► API Gateway ──► Lambda │ ├─► DynamoDB.PutItem (save order) └─► SNS publish "OrderPlaced" │ ├─► SQS-email ─► Lambda send email ├─► SQS-inventory ─► Lambda decrement stock └─► SQS-analytics ─► Lambda log

Pattern 2: Image upload pipeline

User PUT s3://bucket/raw/img.jpg ──► S3 event ──► Lambda resize │ ├─► PUT s3://bucket/thumb/img.jpg └─► DynamoDB.Update image_url

Pattern 3: Scheduled cleanup

EventBridge cron(0 3 * * ?) ──► Lambda cleanup │ ├─► Scan DynamoDB items olderThan 90 days ├─► Delete S3 objects └─► Send SNS report "cleaned X items"

Pattern 4: Fan-out webhook

Stripe webhook POST ──► API Gateway ──► Lambda verify signature │ └─► EventBridge "payment.success" │ ├─► Lambda update order status ├─► Lambda send receipt email └─► Lambda log to Datadog

Pattern 5: Stream processing

App writes order ─► DynamoDB ──► DynamoDB Stream ──► Lambda │ ├─► Update aggregations (total revenue) └─► Index in OpenSearch

Pattern 6: Cache-aside with TTL

Read flow: Lambda ──► Redis.GET key │ HIT ──► return value MISS ──► PostgreSQL query └─► Redis.SET key value TTL 5min └─► return value Write flow: Lambda ──► PostgreSQL UPDATE └─► Redis.DEL key (invalidate cache)

9. 🗑️ Cleanup tất cả

# DynamoDB tables
aws dynamodb delete-table --table-name myapp-orders --region ap-southeast-1

# SQS queues
aws sqs list-queues --queue-name-prefix myapp- --query "QueueUrls[]" --output text | `
  ForEach-Object { aws sqs delete-queue --queue-url $_ }

# SNS topics + subscriptions
aws sns list-topics --query "Topics[?contains(TopicArn, 'myapp-')]" --output text | `
  ForEach-Object { aws sns delete-topic --topic-arn ($_ -split "\s+")[1] }

# EventBridge custom bus + rules
aws events list-rules --event-bus-name myapp-bus --query "Rules[].Name" --output text | `
  ForEach-Object {
    $targetIds = aws events list-targets-by-rule --rule $_ --event-bus-name myapp-bus --query "Targets[].Id" --output text
    if ($targetIds) { aws events remove-targets --rule $_ --event-bus-name myapp-bus --ids ($targetIds -split "\s+") }
    aws events delete-rule --name $_ --event-bus-name myapp-bus
  }
aws events delete-event-bus --name myapp-bus

# ElastiCache
aws elasticache delete-cache-cluster --cache-cluster-id myapp-redis
