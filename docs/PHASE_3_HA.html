1. Tổng quan: HA là gì & tại sao cần

High Availability (HA) định nghĩa

HA = hệ thống vẫn chạy khi 1 thành phần chết. Cụ thể trong AWS:

  • 1 EC2 chết → có EC2 khác đỡ tải
  • 1 AZ (Availability Zone, ~1 data center) chết → resource ở AZ khác đỡ
  • 1 lần deploy fail → tự rollback, user không thấy lỗi

Single Point of Failure (SPOF) hiện tại

ComponentSPOF?Hậu quả nếu chết
1 EC2 (Docker containers)✅ CóToàn bộ site down — frontend, backend, DB, pgAdmin
Docker Postgres trên EC2✅ Có (kèm EC2)EC2 chết → mất container DB → cần restore từ EBS snapshot
Route 53 hosted zone❌ AWS quản (99.99% SLA)AWS lo
S3 + CloudFront❌ AWS quản (đã multi-AZ)AWS lo

A0 Discover hạ tầng hiện có (read-only)

AWS CLI
# 1. VPC default (ALB se chay trong day)
$VPC_ID = aws ec2 describe-vpcs --region ap-southeast-1 `
  --filters "Name=is-default,Values=true" `
  --query "Vpcs[0].VpcId" --output text

# 2. Subnets (can >= 2 AZ khac nhau)
aws ec2 describe-subnets --region ap-southeast-1 `
  --filters "Name=vpc-id,Values=$VPC_ID" `
  --query "Subnets[].{SubnetId:SubnetId,AZ:AvailabilityZone}" --output table

# 3. EC2 hien tai (de biet SG va instance ID se register vao TG)
aws ec2 describe-instances --region ap-southeast-1 `
  --filters "Name=tag:Name,Values=myapp-ec2" "Name=instance-state-name,Values=running" `
  --query "Reservations[].Instances[].{Id:InstanceId,Subnet:SubnetId,AZ:Placement.AvailabilityZone,SG:SecurityGroups[0].GroupId}" --output table

Ghi lại 4 ID cho các bước sau: VPC_ID, danh sách SubnetId, EC2 INSTANCE_ID, EC2 SG.

A3 Tạo Target Group

🚨 CHỌN GIAO THỨC TG QUAN TRỌNG Nginx hiện tại của project listen :80 chỉ để redirect 301 sang :443 (vì cert đặt ở EC2). Nếu TG dùng HTTP:80 → ALB gửi health check tới EC2:80 → nhận 301 thay 200 → target unhealthy mãi với reason ResponseCodeMismatch.

3 cách giải, chọn 1:
  • (Quick — đã làm) Tạo TG với --protocol HTTPS --port 443 --health-check-protocol HTTPS + matcher 200. ALB→EC2 đi qua HTTPS (Let's Encrypt cert vẫn dùng). HTTPS-twice nhưng functional ngay.
  • (Sạch) Sửa nginx/default.conf: thêm location = /api/health { return 200 "OK"; } trong server block port 80 → health check pass mà không phá redirect. Cần commit + redeploy.
  • (Tốt nhất, long-term) Migrate nginx về HTTP-only. ALB lo SSL termination, EC2 chỉ HTTP:80. Cần sửa nginx config, bỏ certbot khỏi morning.ps1, update docker-compose.

UI (option Quick — HTTPS:443)

  1. Console → EC2 → Target Groups → Create target group
  2. Choose target type: Instances
  3. Target group name: myapp-tg-https
  4. Protocol: HTTPS, Port: 443
  5. VPC: default

CLI

$TG_ARN = aws elbv2 create-target-group --region ap-southeast-1 `
  --name myapp-tg-https `
  --protocol HTTPS --port 443 `
  --vpc-id $VPC_ID `
  --target-type instance `

# 1. Tao ALB
$alb = aws elbv2 create-load-balancer --region ap-southeast-1 `
  --name myapp-alb `
  --subnets <subnet-1a> <subnet-1b> <subnet-1c> `
  --security-groups $ALB_SG `
  --scheme internet-facing `
  --type application `
  --query "LoadBalancers[0].{ARN:LoadBalancerArn,DNS:DNSName,Zone:CanonicalHostedZoneId}" `
  --output json | ConvertFrom-Json
# Luu $alb.ARN, $alb.DNS, $alb.Zone

# 2. Listener HTTPS:443 -> forward TG
aws elbv2 create-listener --region ap-southeast-1 `
  --load-balancer-arn $alb.ARN `
  --protocol HTTPS --port 443 `
  --certificates CertificateArn=$CERT_ARN `
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06 `
  --default-actions Type=forward,TargetGroupArn=$TG_ARN

# 3. Listener HTTP:80 -> redirect 301 sang HTTPS
# PowerShell escape JSON inline kho -- ghi ra file tam roi reference
$redirectJson = '[{"Type":"redirect","RedirectConfig":{"Protocol":"HTTPS","Port":"443","StatusCode":"HTTP_301","Host":"#{host}","Path":"/#{path}","Query":"#{query}"}}]'
$tmpJson = [System.IO.Path]::GetTempFileName()
[System.IO.File]::WriteAllText($tmpJson, $redirectJson)

aws elbv2 create-listener --region ap-southeast-1 `
  --load-balancer-arn $alb.ARN `
  --protocol HTTP --port 80 `
  --default-actions "file://$tmpJson"
Remove-Item $tmpJson -Force
ℹ️ Vì sao JSON cho redirect phải qua file PowerShell xử lý #{...} như comment + braces, làm hỏng JSON inline. Ghi ra file tạm rồi file:// reference là cách bền vững.

CLI (phức tạp — phải DELETE + CREATE, không phải UPSERT)

⚠️ Gotcha quan trọng Hiện đang có A record → IP (record thường), muốn đổi thành A record → ALIAS. Mặc dù cả 2 đều là "type A", chúng KHÁC nhau trong Route 53 (alias có AliasTarget, thường có ResourceRecords). UPSERT không hoạt động — phải DELETE record cũ + CREATE record mới trong cùng change-batch (atomic). 
$HOSTED_ZONE_ID = "Z0999500HD1JE8VHHDN2"
$ALB_DNS  = "dualstack.myapp-alb-XXX.ap-southeast-1.elb.amazonaws.com"
# dualstack. prefix recommended boi AWS de support IPv6 sau nay neu can
$ALB_ZONE = "Z1LMS91P8CMLE5"  # CanonicalHostedZoneId tu A4 (KHAC voi hosted zone cua domain)

# Lay tat ca record A cua domain
$allRecords = aws route53 list-resource-record-sets --hosted-zone-id $HOSTED_ZONE_ID `
  --output json | ConvertFrom-Json
$targetRecords = $allRecords.ResourceRecordSets | Where-Object {
  ($_.Name -eq "vhnlong.store." -or $_.Name -eq "www.vhnlong.store.") -and $_.Type -eq "A"
}

# Tao change-batch: DELETE record cu + CREATE alias moi cho moi domain
$changes = @()
foreach ($r in $targetRecords) {
  $changes += @{
    Action = "DELETE"
    ResourceRecordSet = @{
      Name = $r.Name; Type = "A"; TTL = $r.TTL
      ResourceRecords = $r.ResourceRecords
    }
  }
  $changes += @{
    Action = "CREATE"
    ResourceRecordSet = @{
      Name = $r.Name; Type = "A"
      AliasTarget = @{
        HostedZoneId         = $ALB_ZONE
        DNSName              = $ALB_DNS
        EvaluateTargetHealth = $true
      }
    }
  }
}

$changeBatch = @{ Changes = $changes } | ConvertTo-Json -Depth 10
$tmpJson = [System.IO.Path]::GetTempFileName()
[System.IO.File]::WriteAllText($tmpJson, $changeBatch)
aws route53 change-resource-record-sets `
  --hosted-zone-id $HOSTED_ZONE_ID `
  --change-batch "file://$tmpJson"
Remove-Item $tmpJson -Force
💡 EvaluateTargetHealth = true Khi ALB không có target healthy → Route 53 sẽ KHÔNG trả về DNS này (failover nếu có route khác). Hữu ích khi đa region.
ℹ️ JMESPath && trap trong PowerShell Đừng dùng --query "ResourceRecordSets[?Name=='X' && Type=='A']" — PowerShell sẽ encode && thành &amp;&amp; → JMESPath syntax error. Lấy hết về rồi filter trong PowerShell với Where-Object như ở trên.

A7 Verify

5. Module B — Launch Template

Launch Template là gì

Là khuôn mẫu để tạo EC2 instance với cấu hình chuẩn (AMI, instance type, key pair, SG, IAM role, user-data...). Cần thiết cho ASG — ASG dùng Launch Template để biết tạo EC2 thế nào.

Hiện tại morning.ps1 truyền các tham số này vào lệnh aws ec2 run-instances. Launch Template gói chúng lại để tái sử dụng.

B1 Chuẩn bị User Data script

User Data là shell script chạy tự động lúc EC2 boot lần đầu. Đây là cách ASG có thể tạo EC2 mới mà không cần SSH thủ công cài Docker.

Tạo file scripts/ec2-userdata.sh trên local:

#!/bin/bash
# User-data script chay khi EC2 boot lan dau (theo Launch Template).
# Output ghi vao /var/log/cloud-init-output.log
set -e

# Cho apt lock duoc free
for i in {1..60}; do
  if ! sudo fuser /var/lib/dpkg/lock-frontend >/dev/null 2>&1; then break; fi
  sleep 5
done

sudo apt-get update -y

# Docker
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker ubuntu
sudo systemctl enable docker --now

# AWS CLI v2
sudo apt-get install -y unzip
curl -s "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip
unzip -q awscliv2.zip && sudo ./aws/install
rm -rf aws awscliv2.zip

# Khong can certbot/SSL nua -- ALB lo HTTPS, EC2 chi can HTTP

# Tao app dir
sudo -u ubuntu mkdir -p /home/ubuntu/app/production /home/ubuntu/app/staging

# Pull va chay app tu ECR (uu tien IAM role cua EC2)
ENVIRONMENT=production
ECR_REGISTRY=<tu cap nhat ECR_REGISTRY vao day, hoac fetch tu SSM>

APP_DIR=/home/ubuntu/app/$ENVIRONMENT
mkdir -p $APP_DIR/backend
chown -R ubuntu:ubuntu /home/ubuntu/app

# Fetch backend/.env tu SSM (giong nhu deploy.yml dang lam):
#   - get-parameters-by-path lay tat ca /myapp/<env>/* mot luot
#   - awk tach phan cuoi: /myapp/production/DB_NAME -> DB_NAME
#   - Boc gia tri trong '' de an toan voi ky tu dac biet (!, @, $, ...)
aws ssm get-parameters-by-path --region ap-southeast-1 \
  --path "/myapp/$ENVIRONMENT/" --with-decryption \
  --query "Parameters[*].[Name,Value]" --output text | \
awk -F'\t' '{ n=split($1,a,"/"); print a[n]"='"'"'"$2"'"'"'" }' \
  > $APP_DIR/backend/.env

echo "PORT=5000"               >> $APP_DIR/backend/.env
echo "ENVIRONMENT=$ENVIRONMENT" >> $APP_DIR/backend/.env
chown ubuntu:ubuntu $APP_DIR/backend/.env

echo 'USER-DATA DONE'
⚠️ Note User-data này chỉ install dependencies. Để app thực sự chạy cần đẩy docker-compose.prod.yml và pull image. Sẽ làm ở Module E.

6. Module C — Auto Scaling Group (ASG)

ASG là gì

ASG quản lý lifecycle của một nhóm EC2: tự tạo, tự terminate, tự thay thế khi instance lỗi. Có 3 setting quan trọng:

  • min: số EC2 tối thiểu luôn duy trì (vd 1)
  • desired: số EC2 muốn chạy hiện tại (ASG cố giữ con số này)
  • max: số EC2 tối đa khi scale-out

8. Module E — Zero-downtime Deploy

Khái niệm

Hiện tại deploy là big-bang: SSH vào EC2 → docker compose down → up. User thấy 502 trong 30-60s.

Với ASG + ALB, có thể làm rolling update:

  1. Tăng desired capacity 1 → 2 (ASG tạo EC2 mới với version mới)
  2. Đợi EC2 mới healthy trong target group
  3. Giảm desired 2 → 1 (ASG terminate EC2 cũ)
  4. User không thấy downtime

E1 Cách 1 — Instance Refresh (đơn giản nhất)

Instance Refresh là feature của ASG để rolling-replace toàn bộ instances theo Launch Template mới.

AWS Console UI
  1. EC2 → Auto Scaling Groups → myapp-asg → tab Instance refresh
  2. Start instance refresh
  3. Minimum healthy percentage: 50% (giữ ít nhất 50% capacity online)
  4. Instance warmup: 180s
  5. Start

Khi nào dùng:

  • User-data thay đổi → cần boot lại từ template mới
  • AMI mới (vd patch security)

E2 Cách 2 — Sửa deploy.yml để rolling update

Deploy hiện tại SSH vào 1 EC2 và docker compose pull/up. Với ASG có nhiều EC2, cần đổi cách:

# deploy.yml -- thay buoc "Deploy" cu

- name: Get ASG instances
  id: instances
  run: |
    INSTANCE_IDS=$(aws autoscaling describe-auto-scaling-groups \
      --auto-scaling-group-names myapp-asg \
      --query "AutoScalingGroups[0].Instances[?LifecycleState=='InService'].InstanceId" \
      --output text)
    echo "ids=$INSTANCE_IDS" >> $GITHUB_OUTPUT

- name: Rolling deploy (1 instance at a time)
  run: |
    for id in ${{ steps.instances.outputs.ids }}; do
      echo "Deploying to $id"

      # 1. Deregister khoi target group (drain ket noi cu)
      aws elbv2 deregister-targets --target-group-arn <TG_ARN> --targets Id=$id

      # 2. Doi 30s cho draining xong
      sleep 30

      # 3. SSH vao docker compose pull + up
      IP=$(aws ec2 describe-instances --instance-ids $id --query ... --output text)
      ssh ubuntu@$IP "cd ~/app/production && docker compose pull && docker compose up -d"

      # 4. Re-register vao target group
      aws elbv2 register-targets --target-group-arn <TG_ARN> --targets Id=$id

      # 5. Doi health check pass roi moi sang instance tiep theo
      aws elbv2 wait target-in-service --target-group-arn <TG_ARN> --targets Id=$id
    done
ℹ️ Lưu ý Với chỉ 1 EC2 trong ASG (demo), không thực sự là rolling. Cần ít nhất 2 instance. Set desired=2 khi muốn test E2 thật.

13. Troubleshooting

ALB target unhealthy: 502 ở health check

  • EC2 chưa boot xong (user-data đang chạy) → đợi 2-3 phút
  • EC2 SG chưa cho ALB SG vào port 80
  • Backend chưa start xong (container chưa pull image)
  • Nginx config trên EC2 vẫn listen :443 + cần SSL → đổi config khi đã có ALB

ASG luôn thay thế EC2 (loop)

  • Health check grace period quá ngắn → tăng lên 300s
  • User-data fail → check /var/log/cloud-init-output.log
  • App không respond /api/health trong grace period

RDS Multi-AZ tạo thất bại: "InvalidSubnet"

  • RDS subnet group cần ≥2 subnet ở ≥2 AZ → tạo DB Subnet Group trước

Domain vẫn ra IP cũ thay vì ALB

  • DNS cache → ipconfig /flushdns + hard reload browser
  • Route 53 record vẫn type A → IP. Phải edit thành Alias
