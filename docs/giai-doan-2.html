Bước 1 — Security Group

Security Group là firewall của EC2 — kiểm soát traffic vào/ra. Nguyên tắc: chỉ mở đúng port cần thiết, đóng hết còn lại.

Các port cần mở (Inbound rules)

PortProtocolSourceMục đích
22TCP0.0.0.0/0SSH vào EC2
80TCP0.0.0.0/0HTTP (redirect sang HTTPS)
443TCP0.0.0.0/0HTTPS
5050TCPIP của bạn/32pgAdmin production
5051TCPIP của bạn/32pgAdmin staging
8080TCPIP của bạn/32Nginx staging
pgAdmin và staging nên giới hạn source về IP của bạn thay vì 0.0.0.0/0 để tránh expose công khai.

Kiểm tra port có mở không (chạy local)

Lệnh
aws ec2 describe-security-groups \
  --filters "Name=tag:Name,Values=*" \
  --query "SecurityGroups[*].{ID:GroupId,Rules:IpPermissions}" \
  --output table --region ap-southeast-1
Liệt kê tất cả Security Group và inbound rules hiện tại.
Lỗi: site không truy cập được dù app đang chạy
Nguyên nhân: Port chưa được mở trong Security Group.
Fix: Vào EC2 → Security Groups → Inbound rules → Add rule → thêm port cần thiết.

Bước 2 — RDS Revert về Docker DB

RDS là managed PostgreSQL của AWS — data không mất khi EC2 bị xóa. Đây là cách đúng cho production.

Hiện tại revert về Docker PostgreSQL để tiết kiệm chi phí demo (~$23/tháng). Xem docs/RDS_GUIDE.md để migrate khi cần.

Tạo RDS (AWS Console)

FieldGiá trị
EnginePostgreSQL 15
TemplateFree tier
Instance classdb.t3.micro
Storage20GB gp2, tắt autoscaling
Public accessNo
Security Groupmyapp-rds-sg (port 5432, source = EC2 SG)
Backup retention0 days

Tạo database và user trong RDS (chạy trên EC2)

Kết nối RDS bằng master user
psql -h <rds-endpoint> -U postgres -d postgres
Kết nối vào RDS bằng user postgres (master user do AWS tạo).
Tạo user, database, phân quyền
CREATE USER "userPostgres" WITH PASSWORD '<password>';
CREATE DATABASE todos_db;
GRANT ALL PRIVILEGES ON DATABASE todos_db TO "userPostgres";
\c todos_db
CREATE TABLE IF NOT EXISTS todos (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  done BOOLEAN DEFAULT false,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
GRANT ALL ON TABLE todos TO "userPostgres";
GRANT ALL ON SEQUENCE todos_id_seq TO "userPostgres";
\q
Tạo bảng bằng postgres vì RDS PostgreSQL 15 không cho user thường tạo bảng trong schema public.

Cập nhật SSM sau khi có RDS endpoint

Chạy local (PowerShell)
aws ssm put-parameter --name "/myapp/production/DB_HOST" `
  --value "<rds-endpoint>" --type String --overwrite --region ap-southeast-1
Cập nhật DB_HOST trong SSM để backend kết nối RDS thay vì Docker container.
no pg_hba.conf entry ... no encryption
Nguyên nhân: Backend kết nối không SSL, RDS bắt buộc SSL.
Fix: backend/src/db.ts tự bật SSL khi DB_HOST chứa "rds.amazonaws.com". Đảm bảo code mới nhất đã deploy.
password authentication failed for user "userPostgres"
Nguyên nhân: Password trong SSM không khớp với password đặt trong RDS.
Fix: Lấy DB_PASSWORD từ SSM rồi chạy: ALTER USER "userPostgres" WITH PASSWORD '<password>';
permission denied for schema public (code 42501)
Nguyên nhân: RDS PostgreSQL 15 thu hồi quyền CREATE TABLE mặc định của schema public.
Fix: Tạo bảng bằng master user postgres, sau đó GRANT ALL ON TABLE todos TO "userPostgres".

Bước 3 — HTTPS với Let's Encrypt

Certbot lấy SSL certificate miễn phí từ Let's Encrypt. Certificate có hiệu lực 90 ngày, có thể tự động gia hạn.

Yêu cầu trước khi cài

  • Có domain trỏ A record về IP EC2
  • Port 80 và 443 đã mở trong Security Group

Cài Certbot và lấy certificate (chạy trên EC2)

Bước 1 — Cài Certbot
sudo apt update && sudo apt install -y certbot
Cài Certbot lên EC2.
Bước 2 — Dừng nginx để Certbot verify domain
docker stop myapp-production-nginx-1
Certbot cần port 80 trống để verify domain. Dừng nginx tạm thời.
Bước 3 — Lấy certificate
sudo certbot certonly --standalone -d vhnlong.store -d www.vhnlong.store
--standalone: Certbot tự chạy web server tạm trên port 80 để verify. Certificate lưu tại /etc/letsencrypt/live/vhnlong.store/
Bước 4 — Start nginx lại
docker start myapp-production-nginx-1

Cấu hình nginx HTTPS (nginx/default.conf)

# HTTP → redirect sang HTTPS
server {
    listen 80;
    server_name vhnlong.store www.vhnlong.store;
    location / { return 301 https://$host$request_uri; }
}

# HTTPS
server {
    listen 443 ssl http2;
    server_name vhnlong.store www.vhnlong.store;
    ssl_certificate     /etc/letsencrypt/live/vhnlong.store/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/vhnlong.store/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ...
}

Mount certificate vào nginx container (docker-compose.prod.yml)

nginx:
  ports:
    - "80:80"
    - "443:443"
  volumes:
    - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    - /etc/letsencrypt:/etc/letsencrypt:ro  # mount cert từ EC2 vào container
/etc/letsencrypt nằm trên EC2, cần mount vào container nginx mới đọc được certificate.

Kiểm tra certificate còn hạn không

Chạy trên EC2
sudo certbot certificates
Hiển thị tất cả certificate, ngày hết hạn, và domain.
Gia hạn certificate thủ công
docker stop myapp-production-nginx-1
sudo certbot renew
docker start myapp-production-nginx-1
Certbot: Could not bind to IPv4 / port 80 in use
Nguyên nhân: Nginx vẫn đang chạy trên port 80.
Fix: docker stop myapp-production-nginx-1 trước khi chạy certbot.
Certbot: DNS problem / domain not found
Nguyên nhân: A record chưa trỏ về IP EC2, hoặc DNS chưa propagate.
Fix: Kiểm tra bằng nslookup vhnlong.store 8.8.8.8. Chờ 15-60 phút để DNS propagate.
Nginx crash sau khi thêm SSL config
Nguyên nhân: Certificate chưa được mount vào container, hoặc path sai.
Fix: Kiểm tra volumes trong docker-compose.prod.yml có dòng /etc/letsencrypt:/etc/letsencrypt:ro chưa.

Bước 4 — IAM Instance Role

Thay vì hardcode AWS_ACCESS_KEY_ID và AWS_SECRET_ACCESS_KEY, EC2 dùng IAM Role để tự xác thực với AWS. Token tự động rotate, không có key nào để lộ.

Tạo IAM Role (AWS Console)

FieldGiá trị
Trusted entityAWS service → EC2
PoliciesAmazonEC2ContainerRegistryReadOnly, AmazonSSMReadOnlyAccess
Role namemyapp-ec2-role

Gắn role vào EC2

EC2 Console → Instances → chọn instance → Actions → Security → Modify IAM role → chọn myapp-ec2-role → Update IAM role

Verify role hoạt động (chạy trên EC2)

Lấy token IMDSv2 rồi kiểm tra role
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
169.254.169.254 là địa chỉ metadata của EC2 — chỉ truy cập được từ bên trong EC2. Output phải trả về "myapp-ec2-role".
Test thực tế — login ECR không cần credentials
aws ecr get-login-password --region ap-southeast-1 | \
  docker login --username AWS --password-stdin \
  529568113348.dkr.ecr.ap-southeast-1.amazonaws.com
Nếu login thành công mà không cần AWS_ACCESS_KEY_ID → IAM role hoạt động đúng.
curl trả về empty khi gọi metadata endpoint
Nguyên nhân: EC2 đang dùng IMDSv2 (bắt buộc token), không dùng IMDSv1.
Fix: Dùng lệnh có token ở trên thay vì curl trực tiếp.
curl 169.254.169.254: Couldn't connect to server
Nguyên nhân: Đang chạy lệnh trên máy local, không phải EC2.
Fix: SSH vào EC2 trước rồi mới chạy lệnh.
