1. 3 pillar của Observability

Khái niệm chuẩn industry: observability = khả năng hiểu trạng thái nội bộ của hệ thống qua dữ liệu external. 3 pillar:

PillarĐịnh nghĩaService AWSTrả lời câu hỏi
LogsRecord của event riêng lẻ (text, structured JSON)CloudWatch Logs"Lúc 10:23, có gì xảy ra?"
MetricsSố liệu tổng hợp theo time (CPU%, request/s, latency)CloudWatch Metrics"Trend của latency trong 24h qua thế nào?"
TracesHành trình của 1 request qua nhiều serviceX-Ray"Request này tại sao chậm 3s? Ở đoạn nào?"

Cộng thêm 2 pillar mới đang nổi:

  • Audit logs (CloudTrail): ai đã làm gì trên AWS infra
  • Profiling: function nào của app tốn CPU/memory (CodeGuru / OpenTelemetry)
ℹ️ Monitoring vs Observability Monitoring = check dashboard có biết được thứ predefined (CPU > 80%? → alert). Observability = debug được vấn đề KHÔNG PREDEFINED, vd "tại sao 0.5% user gặp 500 error?" — cần logs + traces detailed.

2. Part 1 — CloudTrail

CloudTrail là gì

Ghi lại mọi AWS API call được thực hiện trên account: ai (user/role), khi nào, từ đâu (IP), service nào, action gì, parameters, result. Bắt buộc có cho compliance, security forensics, troubleshooting.

User goes to Console / API call │ ▼ AWS API Gateway (internal) │ ├─► Process request └─► CloudTrail ghi event ──► Event Lookup (90 days, FREE) └─► Trail (S3 bucket, lưu vĩnh viễn)

2 cách dùng CloudTrail

—Event Lookup (default)Trail
SetupCó sẵn, không cần configCần tạo trail + S3 bucket
Retention90 ngàyVĩnh viễn (do bạn quản)
CostFREE$2/100k event ghi vào S3 + S3 storage
SearchUI Console + CLIS3 + Athena query SQL
Use caseDebug 1 vấn đề gần đâyCompliance, long-term audit

Event Lookup (FREE, dùng được ngay)

# 5 event gan day cua user "github-actions-deploy"
aws cloudtrail lookup-events --region ap-southeast-1 `
  --lookup-attributes "AttributeKey=Username,AttributeValue=github-actions-deploy" `
  --max-items 5 `
  --query "Events[].{Time:EventTime,Action:EventName,Resource:Resources[0].ResourceName}" `
  --output table

# Ai vua xoa S3 bucket gan day?
aws cloudtrail lookup-events --region ap-southeast-1 `
  --lookup-attributes "AttributeKey=EventName,AttributeValue=DeleteBucket" `
  --max-items 10

# Tat ca action tren ALB myapp-alb
aws cloudtrail lookup-events --region ap-southeast-1 `
  --lookup-attributes "AttributeKey=ResourceName,AttributeValue=myapp-alb"

Tạo Trail (lưu lâu dài qua S3)

# 1. Tao S3 bucket destination
aws s3api create-bucket --bucket vhnlong-cloudtrail --region ap-southeast-1 `
  --create-bucket-configuration LocationConstraint=ap-southeast-1

# 2. Apply bucket policy cho CloudTrail ghi
# (Policy JSON dai -- xem AWS docs)

# 3. Tao trail
aws cloudtrail create-trail --region ap-southeast-1 `
  --name myapp-trail `
  --s3-bucket-name vhnlong-cloudtrail `
  --is-multi-region-trail `
  --include-global-service-events

# 4. Start logging
aws cloudtrail start-logging --name myapp-trail --region ap-southeast-1

Real-world use cases

  • "Ai xóa nhầm RDS production?" → CloudTrail lookup-events DeleteDBInstance
  • "Ai access AWS account từ IP lạ?" → filter by SourceIPAddress
  • "Khi nào IAM policy bị đổi?" → filter EventName=AttachRolePolicy/DetachRolePolicy
  • Compliance SOC2/HIPAA: bắt buộc trail multi-region, lưu ≥7 năm

CloudTrail + EventBridge: real-time alert

# Rule: alert khi co RootUser hoat dong (forbidden trong prod)

3. Part 2 — CloudWatch Logs Insights

Query language để search/aggregate log như SQL. Game-changer so với grep trên SSH.

Cú pháp cơ bản

# Liet ke 50 dong cuoi cua /ecs/myapp, sorted by time
fields @timestamp, @message
| sort @timestamp desc
| limit 50

# Filter ERROR
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 100

# Count error theo phut (5xx response)
fields @timestamp, @message
| parse @message '"statusCode":*' as status
| filter status >= 500
| stats count() by bin(1m)

# Top 10 endpoint co latency cao nhat
fields @timestamp, @message, path, duration_ms
| filter duration_ms > 0
| stats avg(duration_ms), max(duration_ms), count() by path
| sort avg(duration_ms) desc
| limit 10

Built-in fields

FieldÝ nghĩa
@timestampTimestamp của log event (ISO 8601)
@messageToàn bộ log line
@logTên log group
@logStreamTên stream (mỗi container/instance là 1 stream)
@duration (Lambda)Lambda invocation duration
@requestId (Lambda)Lambda request ID

Run query qua CLI

# 1. Start query
$queryId = aws logs start-query `
  --log-group-name "/ecs/myapp" `
  --start-time (Get-Date -UFormat %s -Date (Get-Date).AddHours(-1)) `
  --end-time (Get-Date -UFormat %s) `
  --query-string "fields @timestamp, @message | filter @message like /ERROR/ | limit 20" `
  --query "queryId" --output text

# 2. Get results (poll until "Complete")
Start-Sleep 3
aws logs get-query-results --query-id $queryId

Logs Insights vs grep — vì sao thay thế

grep trên SSHLogs Insights
Cần SSH vào từng EC21 query qua tất cả log group, mọi instance
Pattern matching cơ bảnFilter + aggregate + groupBy + parse
Mất khi container/EC2 chếtCentralized — tồn tại lâu dài
Không có chartAuto-render line/bar chart từ aggregate query

4. Part 3 — Structured logging

Log dạng JSON thay vì string thuần. CloudWatch Logs Insights tự parse JSON → dễ filter/aggregate.

BAD: unstructured log

console.log("User 100 logged in at 10:23 from 1.2.3.4");
// Output: User 100 logged in at 10:23 from 1.2.3.4
// CloudWatch khong parse duoc field rieng -- phai dung regex phuc tap

GOOD: structured JSON log

import pino from "pino";
const logger = pino({
  level: "info",
  timestamp: pino.stdTimeFunctions.isoTime,
  formatters: { level: (label) => ({ level: label }) }
});

logger.info({
  event: "user_login",
  userId: 100,
  ip: "1.2.3.4",
  userAgent: "Mozilla/5.0...",
  duration_ms: 234
}, "User logged in");

// Output (1 dong JSON):
// {"level":"info","time":"2026-05-25T10:23:00Z","event":"user_login","userId":100,"ip":"1.2.3.4","userAgent":"Mozilla/5.0...","duration_ms":234,"msg":"User logged in"}

Query JSON log dễ dàng

# Logs Insights tu dong parse JSON, expose field nhu first-class
fields @timestamp, userId, ip, duration_ms
| filter event = "user_login" and duration_ms > 1000
| sort @timestamp desc
🎯 Project này đã dùng structured logging Backend code dùng Pino — xem backend/src/config/logger.ts + backend/src/index.ts với pino-http. Log output luôn là JSON. Khi deploy lên ECS + CloudWatch, có thể query qua Logs Insights ngay.

Best practices structured logs

  • Standard fields: timestamp, level, service, requestId, userId (nếu auth), traceId (cho X-Ray)
  • Context fields: action, resource, duration_ms, status_code
  • Don't log sensitive data: password, JWT, credit card → redact
  • Use levels đúng: trace/debug/info/warn/error/fatal
  • Correlate via requestId: cùng request → cùng requestId qua nhiều log line

5. Part 4 — X-Ray distributed tracing

Tracing là gì

1 user request có thể đi qua: ALB → ECS → Lambda → DynamoDB → SQS → Lambda → S3. Trace = bản ghi đầy đủ hành trình đó với latency mỗi đoạn (gọi là span).

USER REQUEST (trace-id: abc-123) │ ├─ Span 1: ALB (5ms) │ └─ Span 2: ECS backend (180ms) │ │ │ ├─ Span 3: DynamoDB GetItem (12ms) │ │ │ ├─ Span 4: Lambda invoke (45ms) │ │ └─ Span 5: S3 PutObject (30ms) │ │ │ └─ Span 6: PostgreSQL query (95ms) ← BOTTLENECK! Total: 185ms

Setup X-Ray cho Node.js app (ECS)

# 1. Install SDK
npm install aws-xray-sdk-core aws-xray-sdk-express

# 2. Wrap app
import AWSXRay from "aws-xray-sdk-express";

app.use(AWSXRay.express.openSegment("myapp-backend"));
// ... routes ...
app.use(AWSXRay.express.closeSegment());

# 3. Wrap AWS SDK clients
import AWS from "aws-sdk";
const wrappedAWS = AWSXRay.captureAWS(AWS);
const s3 = new wrappedAWS.S3();
// Moi S3 call se tu dong tao subsegment

# 4. Wrap HTTP calls
AWSXRay.captureHTTPsGlobal(require("https"));

X-Ray daemon trên ECS

App gửi trace data qua UDP 2000 đến X-Ray daemon, daemon batch upload tới X-Ray service. Trong ECS, daemon chạy như sidecar container hoặc Fargate có built-in.

# Task definition - them sidecar X-Ray daemon
{
  "containerDefinitions": [
    {
      "name": "app",
      "image": "myapp:v1",
      "environment": [{ "name": "AWS_XRAY_DAEMON_ADDRESS", "value": "127.0.0.1:2000" }]
    },
    {
      "name": "xray-daemon",
      "image": "public.ecr.aws/xray/aws-xray-daemon:latest",
      "portMappings": [{ "containerPort": 2000, "protocol": "udp" }]
    }
  ]
}

X-Ray cho Lambda — built-in, chỉ cần bật

aws lambda update-function-configuration `
  --function-name myapp-hello `
  --tracing-config Mode=Active `
  --region ap-southeast-1
# Va them quyen xray:PutTraceSegments vao execution role

Xem trace

  1. Console → X-Ray → Service map: visualize service nào gọi service nào, latency, error rate
  2. Console → X-Ray → Traces: list từng trace với filter
  3. Click 1 trace → waterfall chart của từng span

6. Part 5 — CloudWatch Dashboards

Custom dashboard với widget từ metrics + logs. Dùng để xem nhanh trạng thái app/infra.

Tạo dashboard qua CLI

$dashboardBody = '{
  "widgets": [
    {
      "type": "metric",
      "properties": {
        "metrics": [
          ["AWS/ApplicationELB", "RequestCount", "LoadBalancer", "app/myapp-alb/abc"]
        ],
        "period": 300,
        "stat": "Sum",
        "region": "ap-southeast-1",
        "title": "ALB requests/5min"
      }
    },
    {
      "type": "log",
      "properties": {
        "query": "SOURCE \"/ecs/myapp\" | fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc | limit 20",
        "region": "ap-southeast-1",
        "title": "Recent errors"
      }
    }
  ]
}'

aws cloudwatch put-dashboard --dashboard-name myapp-overview `
  --dashboard-body $dashboardBody

Widget types phổ biến

  • metric: line/bar chart từ CloudWatch metric
  • log: kết quả Logs Insights query
  • text: markdown note
  • alarm: status của alarm (red/green)
  • number: single big number (single value of metric)

Dashboard cho project hiện tại

Đề xuất 6 widget:

  1. ALB RequestCount (line chart)
  2. ALB 5XX error rate (line)
  3. ALB target healthy host count (number)
  4. EC2 CPU% average (line)
  5. Backend error logs (Logs Insights filter ERROR)
  6. RDS connection count (line)

7. Part 6 — Synthetics (uptime monitoring)

Synthetics tạo "canary" — bot tự gửi request đến endpoint của bạn từ AWS, đo kết quả + screenshot. Như UptimeRobot nhưng AWS-native.

Use case

  • Uptime monitor: ping /api/health mỗi 5 phút, alert nếu fail
  • UI workflow test: simulated user login → click checkout → verify success (sử dụng Puppeteer)
  • API contract test: GET /api/products phải trả 200 + array có ≥ 1 item

Tạo canary đơn giản (heartbeat)

Console → CloudWatch → Synthetics → Create canary. Hoặc CLI:

# Script Node.js cua canary (zip file)
const synthetics = require("Synthetics");

exports.handler = async () => {
  const page = await synthetics.getPage();
  const response = await page.goto("https://vhnlong.store/api/health");
  if (response.status() !== 200) throw new Error(`Expected 200, got ${response.status()}`);
};

8. Part 7 — Alert routing

Vấn đề "1 alert = 1 email"

Bị nhiều alarm cùng lúc → email flood → bỏ sót. Production cần routing thông minh: alert nhỏ → Slack, alert critical → SMS/PagerDuty.

SNS topic per severity

CloudWatch Alarm │ ├─► SNS topic "alerts-warning" │ └─► Email + Slack webhook │ └─► SNS topic "alerts-critical" ├─► Email ├─► SMS to oncall phone └─► PagerDuty integration

Setup Slack webhook

# 1. Tao Slack incoming webhook (qua Slack UI)
# 2. Lambda forward SNS message -> Slack

import json
import urllib3
http = urllib3.PoolManager()

def lambda_handler(event, context):
    for record in event["Records"]:
        msg = json.loads(record["Sns"]["Message"])
        slack_payload = {
            "text": f":warning: *{msg.get('AlarmName')}*\n{msg.get('NewStateReason')}"
        }
        http.request("POST",
            "https://hooks.slack.com/services/T00000/B00000/XXXXXX",
            body=json.dumps(slack_payload).encode(),
            headers={"Content-Type": "application/json"}
        )

# 3. Subscribe Lambda vao SNS topic
aws sns subscribe --topic-arn $topicArn --protocol lambda --notification-endpoint <lambda-arn>

9. Part 8 — SLI/SLO/SLA

Khái niệm production: làm sao đo được "app reliability" có objective?

Khái niệmĐịnh nghĩaVí dụ
SLI (Service Level Indicator)Metric đo trạng thái thực tế"99.5% requests <500ms" (actual measurement)
SLO (Service Level Objective)Target nội bộ team muốn đạt"99.9% requests <500ms" (goal)
SLA (Service Level Agreement)Cam kết với khách, có penalty nếu fail"99% uptime hoặc hoàn 10% phí" (contract)

4 SLI quan trọng (Google SRE book)

  1. Latency: thời gian xử lý 1 request (P50, P95, P99)
  2. Traffic: số request/giây
  3. Errors: % request fail
  4. Saturation: tài nguyên đang dùng bao nhiêu % (CPU, RAM, disk)

Cách implement SLO trong CloudWatch

# SLO: 99.5% request co latency < 500ms trong 30 ngay

# 1. Metric tu ALB
#    TargetResponseTime (per request latency)

# 2. CloudWatch metric math
#    e1 = COUNT_OVER(REQUESTS_WITH(TargetResponseTime < 0.5), TARGET_PERIOD)
#    e2 = TOTAL_REQUESTS(TARGET_PERIOD)
#    SLI = e1 / e2 * 100

# 3. Alarm khi SLI < 99.5%

Error budget

Nếu SLO = 99.9% uptime, error budget = 0.1% downtime = ~43 phút/tháng. Nếu đã dùng hết → freeze release, fix reliability trước.
